## 一、最重要的一条：蜕变在卡强化

`StrengthenService` 里原本有这段：

```java
// 锻阶门槛：这一阶已经锻到顶了，先把蜕变打了才能继续往上
EvolutionStage gate = evo.pendingGate(item);
if (gate != null) {
    return refused(item, "已到这一阶的强化上限 +5——先蜕变「精钢」才解锁 +6 以上。/zhujian evolve");
}
```

 Consequences：**强化每走五级就断一次**，被一个有独立界面、独立成功率、独立材料、
独立费用的系统拦住。服主说的「沉浸式强化」不是文案问题——他摸着的是这条断点。

### 为什么这次不是调数值

我一开始只打算把类搬走（`strengthen/` → `evolve/`）。但 `move-evolve`
在核查时把那段门槛文案报了上来，我才意识到：**搬包不解决手感问题**。
类搬到新包，`StrengthenService` 里照样会 `pendingGate` 拦人。

所以做了两层：

| 层 | 处理 |
| --- | --- |
| 代码组织 | 5 个类搬到独立包 `com.forgemaster.evolve`，`strengthen/` 只剩 `StrengthenService` / `Charm` / `Talisman` |
| **玩法耦合** | **删除强化对蜕变的依赖** |

现在依赖只剩单向：

- 蜕变要求剑先锻到某等级（`EvolutionStage.level`）—— ✅ 保留。蜕变的前提本来就是「有一把够强的剑」
- 强化要求先蜕变 —— ❌ 删除

强化上限只认品质（粗糙 +40 / 普通 +50 / 精良 +60 / 史诗 +72 / 传说 +86 / 神话 +99）。
`pendingGate` 保留（蜕变界面要用它展示「下一阶在哪」），但不再参与强化判定。

### 断言改写

原来有一条断言直接锁着旧行为：

```
"门槛拦截：+5 后 pendingGate 非空、锻阶行为空"
```

改成锁**新契约**：

```java
int cap = plugin.strengthen().capOf(sword);
require(cap > 5, "强化上限还是被锻阶压到 +" + cap + "（v2.20 应该只认品质）");
```

这是这类改动的正确姿势：**旧断言不是删掉，是改成锁新行为**。删掉等于把这块覆盖永久弄丢。

## 二、剑体放大的曲线

### 为什么几何插值

线性插值在视觉上是错的。人的眼睛对尺寸是**对数**感知的：1 → 2 是「明显大了一圈」，
7 → 8 几乎看不出来。线性会让 +33 之后每一级都「没感觉」。

几何插值（`S_prev * (S_next/S_prev)^t`）让每一段的手感一致——这正是
「加倍、加倍、再加倍」描述的东西。副作用是它天然压住了低段：+20 才刚起步（×1.1 左右），
强化前期的成长感还在。

```
+20 ×1.00   +33 ×2.00   +66 ×4.00   +99 ×8.00
```

### 曲线是纯函数

`SwordScale` 不碰 Bukkit，所以自检可以逐点断言（0..99 全扫，验单调 + 上限）。
配置写错（乱序、重复、负数、`multiplier ≤ 1`、`NaN`）一律退化成安全值，不抛异常。

## 三、实现：复用已验证的 ItemDisplay 路子

仓库里 `spiritdisplay`（剑灵挂肩侧）已经把这套技术跑通了，直接抄它的生命周期约定：

| 约定 | 为什么 |
| --- | --- |
| `setPersistent(false)` | 崩服 / `kill -9` 不留孤儿实体在存档里 |
| PDC 标记认领（独立键 `big_sword_display`） | 孤儿清扫只认自己的键；**和剑灵共用键会导致「关掉剑灵把大剑一起撤了」** |
| 启动时全量扫孤儿 | 硬崩留下的残留要清 |
| 下线 / 死亡 / 换世界 → 撤 | 换世界后实体留在旧维度，不撤就是永久孤儿 |

更新节奏 2 tick（0.1 秒），`setTeleportDuration` + `setInterpolationDuration` 让客户端插值，
不然硬 teleport 会抖。

位置用视线方向 + 水平右向量算：

```java
Vector right = new Vector(-dir.getZ(), 0, dir.getX());  // 视线绕 Y 转 90°，清掉竖直分量
return eye.add(dir * forward).add(right * side).add(0, -down, 0);
```

清掉竖直分量是关键：否则俯仰时大剑会往天上歪。三个偏移都走配置，因为
资源包和玩家身高不同都会影响手感，写死在代码里意味着服主只能忍着。

## 四、三个诚实的取舍

### 4.1 会看到两把剑

手里那把原版物品是**客户端渲染**的，服务端藏不掉。所以巨型模型套在原版剑外面——
视觉上像「一把大剑里嵌着小剑」。泰坦模组也是类似处理。

要做到只看到一把，必须上资源包（自定义模型 + 按等级切 model）。那是另一个量级的工程，
而且强制玩家装包。这一版选择「服务端就能生效 + 比例连续可调」。

### 4.2 不跟挥砍动画

攻击时大剑不跟着挥。要跟得读 `player.isSwingingArm()` 驱动摆动，
还要处理不同攻速、不同动作。成本高于收益，先不做。

### 4.3 第一人称可能挡视野

8 倍体积的剑在眼前确实占地方。所以有 `per-player-toggle`：
`/zhujian bigsword` 自己关。偏好只存内存——重启恢复默认**开**，
因为重置成「开」比永久留在「关」更不容易让人以为功能坏了。

## 八、追加：装备（护甲）放大与懒人指令

用户追问两句：「装备加大小了吗，满配武器装备有懒人指令吗」。

### 8.1 护甲为什么不能照抄剑的做法

剑是 `ItemDisplay` 挂一团影子模型，位置用视线方向算。护甲不能这样：

- 四件（头盔 / 胸甲 / 护腿 / 靴子）各有各的位置和朝向
- 手写偏移永远会歪，而且和玩家比例、潜行、游泳姿势全都对不上

所以护甲走 **`Attribute.SCALE` 整体缩放**：装备与身体天然同步，走路挥手都跟着走。

曲线按**穿戴护甲的平均强化等级**，+33/+66/+99 → ×1.10 / ×1.21 / ×1.33，上限 1.40。

#### 取平均而不是取最低

取最低等于「必须四件全练」——三件 +99、一件 +0 完全没有效果，手感很挫。
取平均让每一件的投入都算数。`min-pieces: 2` 兜底，穿一件就变大会很怪。

#### 代价必须写进文档

`Attribute.SCALE` 会**同时改碰撞箱和视线高度**：更容易被箭射中、能站进更浅的台阶。
这就是「泰坦体型」的一部分，但确实改变战斗判定——所以护甲上限 1.40，
而剑可以 8 倍（剑是纯视觉，不参与判定）。这个不对称是故意的。

#### 修饰符隔离

挂在独立 `NamespacedKey`（`player_scale`）上。自检专门挂一条「别人的」SCALE
修饰符，验证摘自己的时候不会连累别人的——这是插件之间最常见的打架方式。

`stop()` 必须摘掉：修饰符跟着玩家档案走，不摘的话重载插件后玩家永久变大。

### 8.2 `givefull`：每一维都走真实写入路径

正常路径拿一件满配要几十步且大量掷骰。`/zhujian givefull` 一次给到：

| 维度 | 值 | 路径 |
| --- | --- | --- |
| 品质 / 评分 | 指定品质（默认神话）· 100 | `ItemFactory.buildDirect` |
| 强化 | 品质硬上限（神话 +99） | `StrengthenService.setLevel` |
| 蜕变 | 最高阶 6 阶 | `EvolutionService.forceStage`（新增） |
| 词条 | 上限条数，值取上限，按属性去重 | `Reforge.addAffixRaw` |
| 宝石 | 孔开满，每孔 Lv.5 | `GemService.fillMax`（新增） |

**核心设计：不写死 Lore 文案。** 手写 Lore 会造出「显示造化六阶、属性乘区还是 0 阶」
这种假货——显示对了、数值没生效，是最难查的一类 bug。所以每一维都调用真实写入方法，
最后统一 `strengthen().apply()` 一次。

为此新增两个管理入口，javadoc 都写明绕过了什么：

- `EvolutionService.forceStage` —— 绕过成功率 / 材料 / 费用 / 赛季登记
- `GemService.fillMax` —— 绕过扣费 / 掷命中

`fillMax` 里有两个坑是照抄出来的，也照抄了修法：

1. `freezeEnchantSockets(meta)` 必须在抬宝石孔**之前**——反了的话附魔孔回退值会跟着涨，
   等于白送附魔孔（`socket()` 里同一个坑）
2. 宝石数值走新增的 `GemType.maxAt(grade)`（区间上限 × 等级倍率），
   和 `roll()` 同一套算法，不掷随机。不能随手填一个比真实熔炼还高的数

### 8.3 第二次被自己的检查抓住（这次原因不同）

加完护甲缩放的 5 个配置键，实机跑：

```
✗ 缺 1 个必需键（缺键会静默用代码默认值，服主改不到）
· strengthen.big-sword.player-scale.enabled
```

**这次的原因和上次不一样**：盘上 `config-version` 已经是 8，而 step17 只在版本号
跨过阈值时跑一次——**已经升到 8 的服务器永远不会再跑 step17**。

所以迁移版本号是**一次性闸门**，每加一批键就必须再抬一次。这批单独做
`step18PlayerScaleKeys`，`CURRENT_VERSION` 8 → **9**。复查：**必需键齐全（189 项）**。

两次同类 bug 都是检查器抓的，不是人看出来的。这条经验比功能本身值钱：
**加配置键 → 必须同批加迁移步骤 → 必须抬版本号**，三件事缺一就会出现静默降级。

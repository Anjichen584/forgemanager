## 十四·补十五、v2.25.6：三条 P0 收口 + 砧位并发写盘

上一版把「存档写坏」这一类收掉了，这一版是四路只读审计（落盘 / 经济守恒 / 命令事件 / 权限配置）复盘，
抓到的三条 P0 全部是**能被刷的口子**，不是理论风险：每条都有具体复现路径。

### P0-1 秘境：守卫「失踪」被当成「这一波已打完了」

`tombrun/TombRunService.java` 的 `tick()` 原本这样写：

```java
if (allMissing(run)) {                    // 守卫全都不在了
    if (now - run.missingSince >= 30_000L) {
        waveCleared(run, p);              // ← 当成这一波已清算
    }
    continue;                             // ← 连「跑太远」那一支都被短路掉
}
```

守卫是 `setPersistent(false)` 生成的，**区块卸载就永久消失**。于是：

```
/zhujian tombrun 进场（门票 300）
  → /spawn 站着不动
  → 守卫随区块卸载变成 getEntity(...) == null
  → 30 秒后「第 N 波已清算」，下一波刷在玩家新位置
  → 约 90 秒后「秘境试炼通关」：800 剑币 + 2 残页
```

零战斗、无冷却、可无限重复。而 `config.yml` 里 `away-seconds` 的注释写的是
「**跑远/守卫失踪多少秒后判负**」—— 实现方向和配置完全相反，实现还硬编码了 30 秒、根本没读那个键。

修法：抽出纯函数 `missingAction(missingSince, now, awaySeconds)`，宽限期内只能 `WAIT`、
宽限期满只能 `FAIL`；枚举里**不允许**出现第三种「清算」语义，以后谁改回去自检当场红。

### P0-2 剑冢挑战：退服把整张冷却表删了

`tomb/TombChallenge.java` 的 `onQuit` 第一行是 `cooldowns.remove(quitId)` —— 删的是该玩家
**整张**冷却表。而斩影成功是会记冷却的，于是「打赢 → /quit → 重连」就能立刻重打同一把剑，
`cooldown-hours = 24` 形同虚设，同一把剑变成无限材料/彩头来源。

修法：抽出 `pruneExpired(mine, now)`，退服只回收**已过期**的条目（内存契约仍然成立），
生效中的冷却一律留着。

### P0-3 订单托管：扣剑币、退金币 = 1:1 洗钱口

`order/OrderService.java` 的 `post` 用 `stats().takeCoins` 扣**剑币**，而三条退回路径
（取消退单、交付发赏、过期退款）早就切到了 `wallet()`。在 `economy.coin-sinks: server` 的服上：

```
/zhujian order post 1000000   → 扣剑币（主手样品不消耗）
/zhujian order cancel <id>    → 退 Vault 金币
```

一个循环就把剑币洗成服务器金币，无上限。README 的 A/B/C 表把「订单托管」明确划在 Wallet 侧，
`audit/30-fix-econ.md:109` 记的就是这个「越界未改」。修法：`post` 改走
`wallet().take(p, bounty, CoinReason.OTHER_OUT)`，提示文案里的币名跟着 `wallet().ledgerName()` 走，
不再写死「剑币」。

### 附带：砧位写盘的并发层（审计报的第 4 条 P0）

`anvils.yml` 是唯一装着玩家**实物剑**的存档。上一版给它接了原子写，但有两个洞：

- `YamlIo` 的临时文件名固定为 `<name>.tmp` —— 两个线程同时 save 同一份存档会往同一个 tmp
  里各写一股字节流，交错成半截/混杂 YAML，`ATOMIC_MOVE` 顶上去就是坏档。
  自检里 8 线程并发写当场复现（3 次抛异常）。
- `AnvilForgeManager.saveTo` 的 `synchronized` 只圈住「拍快照」，写盘在锁外。
  一次 5 秒异步冲刷正在写盘时执行 `/zhujian reload`（stop→save）或 `backup restore`（flushAll→save），
  两路并发；`stopFlushTask()` 只能取消任务 id，拦不住已经在跑的线程。

后果两种，都很糟：**旧快照压掉新快照**（玩家已取回的剑重新出现在文件里 → 复制）或**坏档**
（砧位上所有剑一起失踪）。

修法三处：
1. `YamlIo` 临时文件名带 `pid + tid + nano`，并按**目标文件绝对路径**取锁（不依赖 40 多个调用点各自记得加锁）；`ATOMIC_MOVE` 撞上杀软占用时重试 3 次。
2. `saveTo` 整段（快照 + 写盘 + 清脏）进同一把锁，后进入的那次拍到的一定是更新的快照。
3. `stop()` 写盘失败时**不再 `sessions.clear()`** —— 原来是「内存清空 + 文件还是旧的」，
   剑既不在背包也不在文件里；现在写不进去就保留内存并 `SEVERE` 报出来。

### 新增：`/zhujian anvil` 砧位自查

上一版修了「砧位上的剑会丢」，但玩家**没有任何办法**确认自己的剑还在不在 ——
超时回收、方块被拆、区块卸载都可能让剑回到背包或掉在砧上，人不在跟前根本不知道。
现在：

```
/zhujian anvil        # 我的剑：世界 x,y,z | 品质 +强化 | 放了多久、还剩多久自动还
/zhujian anvil all    # 管理员：全部砧位 + 主人名
```

纯只读：只遍历 `sessions()` 打印，不碰 ItemStack、不刷新实体、不落盘。

### 本轮钉子（520 项，新增 3 条语义钉子 + 1 条并发钉子）

1. **秘境失踪必须判负**：钉的是语义不是文案 —— `MissingAction` 只许有两个值，宽限期内 `WAIT`、
   期满 `FAIL`；顺带断言 `away-seconds` 真的被读到（防退回硬编码 30 秒）。
2. **冷却只清过期**：`{生效中, 已过期, 脏 null}` 三条一起喂进去，只许留下生效中的那条。
3. **订单托管不许再出现 `stats().takeCoins`**：扫 `OrderService.java` 源码（跳过注释），
   一处命中就红；同时要求 `wallet().take` 存在、`ledgerName()` 非空。
4. **YamlIo 并发写**：8 线程 × 20 轮写同一份存档，要求零异常、目标文件可读、不留 `.tmp` 垃圾。

## 十四·补十四、v2.25.5：T0 收口（存档原子写 + 坏档留档）

服主一句「不求多，至少保证目前的没什么严重 t0bug」，于是这轮**不做新玩法**，只做四路只读审计：
落盘/异步冲刷、物品与经济守恒、命令与事件健壮性、权限与配置。三路结论是「无 T0」（附覆盖清单），
落盘那一路抓出真问题。压测与自检的数字最后一起给。

### 一、根因：70 多处裸 `yml.save(file)` + 「解析失败静默当空档」

Bukkit 的 `YamlConfiguration.save(file)` 是**覆盖式直写**，不是原子操作。于是有一个三步连环：

```
写到一半崩/断电/盘满  →  留下半截 YAML
        ↓
下次 loadConfiguration 解析失败只打一条 warning，返回**空配置**
        ↓
各存储类 load() 见空 → return（"这个玩家没档案"）→ 首次业务变更触发全量重写
        ↓
          原件在内存里被覆盖，人工抢救的机会也没了
```

新增 [`util/YamlIo.java`](../../src/main/java/com/forgemaster/util/YamlIo.java)：

- `save(file, yml)`：先写同目录 `<name>.tmp` → `fsync` → `ATOMIC_MOVE` 顶掉目标（不支持原子移动的文件系统退化成 `REPLACE_EXISTING`）。**任何时刻目标文件要么是旧的完整内容，要么是新的完整内容**。
- `loadOrQuarantine(file, owner, log)`：文件**非空却读不出任何键**（或直接抛 `InvalidConfigurationException`）时，把原件改名成 `<name>.corrupt-<时间戳>` 留在原地，再返回空配置 —— 数据用不了，但服主手上还有东西可救。0 字节文件视为「第一次跑」，不动它。

### 二、三个真 T0

| 存档 | 装着什么 | 坏了会怎样 |
| --- | --- | --- |
| `anvils.yml`（[AnvilForgeManager:1452/1534](../../src/main/java/com/forgemaster/anvil/AnvilForgeManager.java#L1534)） | **砧位上玩家的实物剑**（`place()` 时已从背包取出） | 半截文件 → 重启后砧位表空 → 剑凭空蒸发，且原件被覆盖。**这是唯一装着实物剑的存档，原来完全没保护** |
| `pass-data.yml`（[SeasonPassService](../../src/main/java/com/forgemaster/pass/SeasonPassService.java#L341)） | premium **付费轨已购状态** + 赛季积分 + 已领级数 | 归零后付费状态不可再生（真金白银买过），已领记录清空还能重领 |
| `codex-data.yml`（[CodexService:120](../../src/main/java/com/forgemaster/codex/CodexService.java#L120)） | 图鉴 `claimed` 领取凭据 | 清空 = **6 个分类奖励 + 全收集奖励可以重领一遍**，`addCoins` 直接产出剑币 —— 不可逆的经济污染 |

### 三、两个「同型」缺口

- **`pass` 的清脏条件恒真**（[SeasonPassService:325](../../src/main/java/com/forgemaster/pass/SeasonPassService.java#L325)）：`if (wasDirty && dirty) dirty = false;` —— `wasDirty` 和 `dirty` 是**同一个 volatile 布尔**，进方法时必然都 true，条件恒成立，等于「无论写盘窗口内有没有新变更一律清脏」。窗口内 `markDirty` 的那一笔从此没有重试路径。照 `ContractStore` 的口径改成 `dirtySeq` 代数：组装前取 seq，落盘后 seq 没前进才清脏。
- **契约入贡 30 秒吞剑**（[ContractManager:325](../../src/main/java/com/forgemaster/contract/ContractManager.java#L325)）：`deposit()` 先 `setItemInMainHand(null)` 再只 `markDirty()`，而 `ContractStore` 的异步冲刷是 600 ticks = **30 秒**。窗口内崩服 = 剑两头都没有（池子没涨、手里也没了）。这跟 v2.25.2 修过的 `TombManager.bury` 是完全同型的缺口，当时漏了这一处；现在同样补一次同步落盘。

### 四、顺手收的两个非 T0

- [BountyManager:222](../../src/main/java/com/forgemaster/bounty/BountyManager.java#L222)：`Quality.values()[b.minQuality()]` 没钳制（同文件记录构造器有 `Math.min`，这里漏了），且 `q.display()` 在品质名改过之后会 NPE。钳一下、兜一个「未知品质」。
- [ForgeManager:2244](../../src/main/java/com/forgemaster/forge/ForgeManager.java#L2244)：`reclaim()` 关的是「任意 ForgeHolder」而非本会话那张，会把玩家另开的锻造界面一起关掉（`giveResult` 幂等所以无复制，纯界面误伤）。补 `h.session() == s`。

### 五、钉子（这次钉的是「以后别再犯」）

1. **`YamlIo` 行为钉子**：原子写后内容正确且 **不留 `.tmp` 残留**；半截文件必须被改名留档（原文件消失 + 出现 `.corrupt-*` + 返回空配置）；0 字节新档不许被当成坏档移走。
2. **存档守卫钉子**：点名 13 份「必须有 YamlIo」的存档，逐个扫源码，少一个就红。这条钉子自己踩过两个坑，都写进注释了：
   - 第一版用 `getDataFolder().getParentFile()` 推源码路径 —— 永远推不到，等于**假绿的钉子**；
   - 第二版向上找「第一个命中」，结果命中了 `ForgingMaster/` 里那份 **2.10.6 的旧源码树**，把改好的判定成没改 —— **假红**。现在给候选打分：含 `util/YamlIo.java` 的优先，其次 pom 版本与运行时一致。

## 十四·补十三、v2.25.4：压测面扩到 12 阶段、账本口径分类

上一版是 7 个并发面（签到 / 秘境 / 黑市 / 拍卖 / 行会 / 铁砧 / 掉线），只覆盖了「玩家之间抢钱」那一类。

### 二、`/zhujian stats rep give|take <玩家> <数量>`（声望的第一个手动入口）

声望以前只有玩法内部产出（锻造 / 委托 / 大赛 / 比试 / 剑冢 / 成就 / 剑谱 / 订单），
想补一次掉档的声望、或造一个「刚好够兑换一次」的号，只能去改 `data.yml` —— 而 `StatsStore`
是内存缓存 + 全量重写，改了下次 `save()` 就被盖回去，还得重启。

- `give` 走 `addReputation`，`take` 走 `spendReputation`（**不足拒付，不会扣成 0**），同一份 `Stats.reputation` 字段
- 落在 `stats` 下面而不是新开顶层命令：声望的读数本来就在 `/zhujian stats`（`声望 N`），读写同一个门
- 补全：第二段「玩家名 + `rep`」并列（老行为不变），选 `rep` 之后才是 `give|take` → 玩家名 → 数量
- **不走 Wallet**：声望不是货币，与 `economy.coin-sinks` 无关

## 十四·补十一、v2.25.2：4 并发实测 + 查错轮4（21 条全修）

先用 `tools/guitest/concurrent4.js`（4 个 mineflayer bot 同 tick 抢同一个模块）跑真机并发，再让两个只读 agent 扫「持久化/异步冲刷」与「GUI/经济共享态」。**实测没抓到玩家能复现的重复扣钱/复制物品** —— 抓到的 21 条全是「只在崩溃窗口、异常路径、退服重进时成立」的潜在缺陷，这类缺陷的特点是平时全绿、出事就是一整本账。

### 一、异步冲刷任务被异常打死（最要命的一类，8 条）

Bukkit 的重复任务**抛一次异常就被永久取消**（`AnvilForgeManager:1483` 早就写过这条注释）。6 个存档的 5 秒/5 分钟冲刷在此之前没有任何 try/catch：一次 CME 或外部经济回调异常，`data.yml`、`guild-data.yml`、`tombs.yml`、`auction.yml`、`anvils.yml`、`contract.yml` 就从那一刻起**静默不再落盘**，只能重启救 —— 而玩家的委托「已领」、通行证「已领」、仓库物品全靠这些文件。

- `StatsStore` / `GuildService` / `ContractStore` / `TombManager` / `AuctionStore` / `AnvilForgeManager` / `SeasonPassService` 的冲刷与 `save()` 全部补 try/catch（记日志 + 保持脏，下一轮重试）。
- `AuctionManager.settleExpired()`（每 5 秒）与 `ContractManager.tickClock()`（每 20 tick）是主线程任务，同款问题：单张拍品/单日结算出错就永久停摆（拍品再也不到期、卖家永远收不到钱）。改为逐条目 try/catch + 跳过本轮，下一轮自然重试。
- `SeasonPassService.save()` 原来先 `dirty = false` 再写盘，写失败就永久丢脏 → 改为写成功且代数未变才清脏。

### 二、快照拷贝在 try 之外（CME 逃出去就整文件不写）

`new LinkedHashMap<>(cache)` 这类拷贝在主线程正在改的裸 `HashMap` 上执行会抛 CME。原来只有「拷贝本身」包在 try 里、而拷贝操作在锁外/在 try 外，异常直接逃出 `save()`。

- `StatsStore.cache` 换 `ConcurrentHashMap`（剑币主账：主线程 `computeIfAbsent` 建档触发 resize 时，异步线程正在拷快照，裸 HashMap 不只是抛异常，结构都可能写坏）。
- `GuildService`（行会列表 + 委托 + 仓库三份快照）、`ContractStore`（`r.relics` 拷贝）、`TombManager` 全部把拷贝收进 try，失败就 `return` 并保持脏。
- `ContractStore.save()` 改成**装配前**先取 `dirtySeq`，写完只在代数未变时清脏（`AnvilForgeManager` 同款）。

### 三、跨文件交接不同步（丢道具/丢钱窗口）

- `OrderService.addMail()` 只把 `auction.yml` 标记为脏就返回 → 5 秒窗口内崩服/重启，交付的剑彻底消失（单据已结、邮箱没有）。改为当场 `store().save()`。
- `TombManager.take()` 先给物品后落盘 → 5 秒内崩服可复制一把；`bury()` 清主手后异步落盘 → 崩服吞掉一把。两处都改为**先落盘、后交货 / 清手后立即落盘**。

### 四、两本账漏改（coin-sinks=server 时凭空铸币）

`ShopManager.buy()`（商会采购）与 `OrderService`（悬赏托管、交付结算、取单退款）直连 `stats().takeCoins / addCoins`，绕开 `Wallet`。服务器接 Vault 时，扣的是剑币、退的是金币（或反之）—— 与 v2.23.1 修的黑市/签到同源。全部收口 `Wallet`。

### 五、退服不清的二次确认状态（误扣 5000 剑币）

- `PassGuiRouter` 的付费轨「已武装」是 static per-uuid 表，只有 /reload 与 3 秒过期会清：点一下武装 → 立刻退服 → 3 秒内重进 → 再点同一格 = 一跳过确认直接买断。补 `PlayerQuitEvent` 清理。

## 十四·补十六、v2.25.7：四条 P1 收口（钱货时序）

> 承接 v2.25.6 的三条 P0。这一轮不碰新玩法，只处理「钱和货的先后顺序」——
> 这四条单看每条都不致命，但共同点是**崩服一次就白送**，而崩服不总是玩家的错
> （OOM、插件冲突、管理员重启）。一晚上撞上一次就是真的损失。

### 一、付费轨：先扣钱、后记录 → 先落盘、再扣钱

`pass/SeasonPassService.java` `buyPremium` 原顺序：

```java
wallet.take(player, 5000, PASS_PREMIUM);   // 钱先没了
progress(uuid, seasonNumber()).premiumBought = true;
save();                                     // 失败只 warning
```

写在内存里的「已购」要等 30 秒异步 flush 才落盘。崩在这中间 = **花了 5000 什么都没拿到**，
而且玩家手上没有任何凭据。反过来，如果这里改成「先记录后扣钱」而不管 save 结果，
就会出现「没扣钱却有付费轨」（更糟，是造币/白嫖）。

正确做法是让 `save()` **能报告成败**，然后按「记录 → 落盘 → 扣钱」严格排序，两头都留回滚：

```java
boolean wasBought = prog.premiumBought;
prog.premiumBought = true;
if (!save()) { prog.premiumBought = wasBought; /* 一分没扣，提示稍后再试 */ return false; }
if (cost > 0 && !wallet.take(player, cost, PASS_PREMIUM)) {
    prog.premiumBought = wasBought; save();   // 钱没扣到 → 撤回「已购」
    return false;
}
```

两种失败都不会让玩家吃亏：盘写不了 → 一分不扣；钱扣不了 → 已购回滚。

**改动**：`public void save()` → `public boolean save()`（`SeasonPassService.java:324`）。

### 二、领奖记录落盘失败不再静默

免费轨（`:608-622`）与付费轨（`:706-717`）原来是「发奖 → 裸 `save()`」。奖励已经进背包，
而「已领」只在内存里 + 脏标记等下一轮 flush。崩在这 30 秒内，重启后**这一级可以再领一次**。

这一条不能简单地改成「先落盘再发奖」—— 那样崩在中间就变成「记录有、奖励没发」，
玩家反而吃亏且更难查。所以保留「发奖在前」，但把失败**说出来**：

```java
if (!save()) {
    logger.severe("第 N 级：奖励已发放，但已领记录落盘失败（uuid=…）。脏标记已置位，"
            + "后续 flush 会重试；若在重试成功前重启，该玩家可重复领取这一级，请对账。");
    Msg.prefix(player, "<yellow>奖励已发放，但存档暂时写不进去，已排队重试。</yellow>");
}
```

判据：**这类窗口无法用排序消除**（发奖与记账不是原子操作），能做的是「不静默 + 留对账线索」。
日志里带 uuid、级数、钱数，管理员能直接定位。

### 三、黑市限购：计数写在发货之后 → 先占额度

`blackmarket/BlackmarketService.java` 原顺序是「扣钱 → 发货 → `recordPurchase` → `save()`」。
崩在发货和落盘之间，今日额度回到满值 —— 配折扣价就是**崩溃刷折扣货**。

修法是把「额度」当成需要**预留**的资源（和数据库的 `SELECT FOR UPDATE` 一个意思）：

```java
if (!store.tryReservePurchase(id, date, offerKey, limit)) {
    wallet.give(p, price, REFUND);        // 没占上额度 → 不发货、钱原路退回
    return;
}
ItemStack goods = buildItem(offer);
if (goods == null) {
    store.releaseReservation(id, date, offerKey);   // 货坏了 → 额度也放回去
    wallet.give(p, price, REFUND);
    return;
}
```

`DailyStore` 新增三个方法：`tryReservePurchase`（占额度 + 落盘，成功才返回 true）、
`releaseReservation`（撤回，减到 0 就清掉空壳）、`save()` 改返回 boolean。

**写这条钉子时踩了个真坑**：第一版自检用假日期 `SELFTEST-DATE`，测出来「占额度后计数没涨」。
原因是 `DailyStore.save()` 会剪掉「非今天/非昨天」的日期层，假日期当场被剪掉。
改成 `DailyStore.today()` 才通过 —— 这条钉子反过来证明了剪层逻辑是真的在跑。

### 四、`wallet().give` 返回值不许再丢

| 位置 | 场景 |
| --- | --- |
| `order/OrderService.java:325` | 交付发赏给接单人 |
| `order/OrderService.java:368` | 取消退单退款 |
| `commission/CommissionManager.java:400` | 委托交货给币 |

`give` 返回 false = 这笔钱没进玩家账户（离线、经济插件不可用、数额非法）。以前直接丢掉：
玩家点了「取消」，单据删了、钱没到，**事后既没有日志也没有告警**，只能等玩家来投诉。

照抄拍卖行的 `warnLost` 做法，在 `OrderService` 加了自己的 `warnLost(uuid, name, amount, what)`：
写 `SEVERE`（带 uuid/金额/单号，可直接人工补发）+ 给玩家留一条邮箱提示。

### 五、`anvil-forge.enabled` 补到落锤路径

这个开关原来**只在 `place()` 判**（`AnvilForgeManager.java:258`），`strike`/`strikeBatch` 都没判。
服主维护期设成 false 想停强化，结果已经摆在场上的砧位照样能单锤、批量还能连跳冷却；
更糟的是此时 `capOf()`/`costOf()` 已经切回旧口径曲线，和玩家刚才看到的上限/费用当场对不上。

补在两处，且**放在「冷却静默」判断之前** —— 关停时必须给一次提示，不能一声不响。

### 六、钉子与真机结果

- **黑市额度可占可撤**：占 → 读得到 → 撤 → 归零 → 买满拒 → 多次占满后全撤不残留 → 撤不存在的记录不炸。
- **通行证 `save()` 能报告成败**：正常环境必须返回 true（否则买付费轨永远被拒）。

```

```

## 十四·补十七、v2.25.7 续：并发放到 5、连续轮次、以及「429 到底会不会断」

### 一、连续轮次（不留空档）

原来定时器是每 3600 秒敲一次，一轮跑 10-15 分钟 —— 中间必然空等 45 分钟。
改成 **600 秒**：一轮干完时下一轮的提醒基本已经在排队，所以「这一轮结束＝下一轮开始」。

为什么不设成 60 秒「绝对无缝」：那样一轮里会排出十几条提醒，轮次结束会被连珠炮式触发，
每轮都要完整跑一遍构建+自检+压测，纯烧时间和额度。600 秒的取舍是：
**最多空等 10 分钟，但绝不会堆出多条**。真要做到零空档，应该改的是「一轮的任务量」而不是提醒频率。

### 二、并发 4 → 5，实测上限

| 并发 | 结果 |
| --- | --- |
| 4 | PASS 56 / WARN 0 / FAIL 0（老默认） |
| **5** | **PASS 63 / WARN 0 / FAIL 0**（现默认，多 7 条断言） |
| 6 | 上线 12.6 s，存活 6/6，0 次节流 |
| 8 | 上线 14.3 s，存活 8/8，0 次节流 |

第 5 个 bot 不是摆设：集合类阶段（签到、剑冢、黑市、商会、竞价、只读风暴）都会遍历全体，
多一个参与者就多一组断言。

### 三、429 是个伪问题（在本机）

bot 用 `auth: 'offline'`，服务端 `online-mode=false` —— **握手全程不碰 Mojang 会话服**，
那个会返回 HTTP 429 的接口从来没被调用过。实测 5/6/8 并发 0 次节流。

真 429 只出现在**在线模式**（多账号同时认证被限流），属于网络/账号层面，不是插件逻辑。
所以「加个 sleep」不是正解，正解是**退避 + 抖动**：

- 固定 sleep 的问题：限流按时间窗放行，睡固定时长容易反复撞同一堵墙。
- 指数退避（1.5s → 3s → 6s → 12s）+ 0~800ms 抖动：把多个 bot 的重连拆开，
  避免它们同时再撞一次。

实现落在 `tools/guitest/concurrent4.js` 的 `joinWithRetry`，最多 4 次，节流计入
`throttleEvents` 写进报告，**记 WARN 不记 FAIL**。

### 四、8 并发失败那次，报的其实不是 429

`BOT_COUNT=8` 直接 `multiplayer.disconnect.server_full` —— 测试服 `max-players=5`。
这是**硬性拒绝**，重试只会白等 4 轮还把真原因埋掉。现在脚本会立刻停下并说明
「这通常是 max-players 满了或不在白名单，不是 429」。

顺手修了两个日志 bug：
- `sp()` 里用 `bot.username` 报错，被踢时它还是 `undefined`，日志打出「undefined 被踢」，认不出是哪只。
  改成用传入的 `name`。
- `sp()` 只等 `spawn`，被踢要傻等满 20 秒。现在同时监听 `kicked`/`error` 立刻失败。

### 五、定时任务会不会被 429 弄断

**不会。** 定时器是独立的，压测红了只是这一轮的结论是红的，提醒照常。
真正的风险是「一轮 FAIL 被当成环境抖动糊过去」，所以规则里写死：
红了先 `BOT_COUNT=4` 重跑 —— 4 也红＝真回归；只有 5 红＝并发面真被撞出问题（这是好事）。

### 六、探针与回归分离

新增 `JOIN_ONLY=1`：只连、空转 20 秒、出报告就退。用途是「测连接行为」而不污染 12 阶段回归门。
两者混在一个开关里，就会出现「探针一抖，回归门假红」。

脚本名保留 `concurrent4.js`（`run-stress.py` 和一堆文档按这名字引用），
但并发已可配 —— 名字不再等于并发数，这点写进了 `docs/dev/build.md`。

## 十四·补十八、v2.25.7 续：连接上限归因实测（不是 429，也不是 IP 节流）

### 起因

之前一直把「并发上不去」归因成 429 或 IP 节流，依据只是「感觉」。这一轮写了
`tools/guitest/netprobe.js`，把四种可能**逐个单独测**，每段只改一个变量。

### 实测

| 段 | 测什么 | 结果 |
| --- | --- | --- |
| A | 同 IP **150ms** 间隔连 8 次（打 `connection-throttle: 4000`） | **8/8 成功，0 节流** |
| B | burst 12（`max-players=12`） | 12/12 成功，621ms |
| B | burst 20（`max-players=12`） | **12 成功 / 8 次 FULL** |
| B | burst 24（`max-players=24`） | 24/24 成功，4387ms |
| C | 逐个连 24 个 | 24/24，18.3s，平均 764ms |
| D | 24 个停留 20s | 存活 24/24，0 被踢 |

### 结论

1. **本机永远不会 429** —— 离线模式握手不碰 Mojang 会话服。真 429 只在在线模式。
2. **`connection-throttle: 4000` 不起作用**：150ms 连 8 次全过。它拦的是「同一瞬间堆叠」，不是「4 秒内不许再连」。
3. **唯一硬墙是 `max-players`**：20 个里恰好 12 个成功 / 8 个 `server_full`，数字对得上就是证据。
4. **`max-joins-per-tick: 5` 只排队不拒绝**：burst 24 全成功，但耗时 621ms → 4387ms。

### 「加个 sleep」为什么不是正解

限流按时间窗放行，固定 sleep 容易反复撞同一堵墙。正解是**令牌桶限速 + 指数退避 + 抖动**，
且**有代理时优先换出口**（限制多半跟 IP 走，换 IP 比等窗口快得多）。

实现落在 `tools/guitest/connpool.js`，按失败原因分流：

| 特征 | 归类 | 处理 |
| --- | --- | --- |
| `server_full` / 白名单 / 封禁 | 硬性拒绝 | **立刻报错，绝不重试** |
| `Connection throttled` | 同 IP 节流 | 换出口 + 退避 |
| `429` | 认证限流 | 退避 + 抖动 + 换出口 |
| `ECONNRESET` / `ETIMEDOUT` | 网络抖动 | 同出口退避（换代理反而引入新变量） |

最关键的一条：**把硬限当 429 去重试**会白等 4 轮还把真原因埋掉。上一轮 8 并发
`server_full` 被误判成 429 就是这个坑。

### 顺带修掉一个测试装置的几何 bug

平台尺寸原来**写死 4 人份**（`fill` 到 `BX+14`）。并发提到 8 之后，第 6~8 个 bot 站在
`BX+15` 以外 = 悬空、掉下去、块卸载，`blockAt` 读回 `null`，于是报「砧位没放成」。
那不是插件的锅，是测试装置把地盘算小了。改成按 `bots.length` 算，WARN 从 6 归零。

## 十四·补十九、v2.25.8：签到与取剑的两处钱货时序

上一轮列了四条待办。这一轮做完发现**一条是误判**，另外两条是真事故。

### 一、签到发奖：币到手、记录回滚 = 可以反复刷

原顺序（v2.25.2 改过一次，但没改透）：

```
记签到 → save → wallet.give（币进钱包）→ 造材料（可能抛）→ 造符（可能抛）
                                                  ↓ 抛了
                                          catch: 只回滚 setSignin
```

问题在于 catch 回滚的是**签到记录**，而不是**已经发出去的剑币**。于是玩家拿到币、
签到记录被清掉，下次进来还能再领 —— 比「先发奖后记账」更容易刷。

关键认识：**会抛异常的不是「发」，而是「造」。** `materialItem()` 遇到配置里写错的材料 id、
`Charm.create()` 遇到注册表缺件或堆叠上限冲突，才会抛；而 `wallet.give` 和
`inventory.addItem` 是「进背包或掉地上」，不抛。

所以修法是把构造整体提到发东西之前：

```
造材料 → 造符（这一步抛：一分钱一件货都没发，进度也没动，直接 return）
记签到 → save
给币 → 进背包
```

过了构造这一关，后面不再有可抛点，原来的 try/catch 整段可以删掉。
`blackmarket/DailyRewardService.java:128-200`

### 二、取剑：写盘失败也把剑发出去了

`TombManager.save()` 是 `void`，写失败时内部 `warning` 一声就完事。于是磁盘满 /
文件被占用时：`tombs.remove()` → `save()`（失败，只打日志）→ `giveItem()`。
结果剑进了玩家背包，而 `tombs.yml` 里那把剑还在 —— 重启后又有一把（复制）。

修法：新增 `boolean saveChecked()`（`save()` 改为直接调它），取剑路径改成

```
若 !saveChecked():
    把条目放回内存 → 退费 → SEVERE 日志（含玩家/编号/金额）→ 不交剑
```

判据很清楚：**「存不进去就别交东西」**。这类路径要的是成败，不是"尽力而为"。
`tomb/TombManager.java:243-300`、取剑处 `:565-600`

### 三、碎剑留档可挑战 —— 这不是漏洞，是我上一轮误判

上一轮把「`canNurture` 有 broken gate、挑战没有」列成 P1。这一轮查了三处证据：

1. `TombChallenge.levelOf()` 里有一支 **专为 broken 写的分支**：
   `if (t.broken) level = Math.max(level, t.brokenAt);` —— 只有挑战路径会调 `levelOf`。
   若 broken 不该被挑战，这段就是死代码。
2. `gameplay.md:391` 写的是留档「**不能 take() 取回**、**不占埋剑名额**」，没写不能挑战。
3. 设计语义也说得通：留档是废铁，取不回来；但残影还能打，而且按「碎在 +N」更强。

结论：**保持行为不变**。加了一条自检钉子把这个判断固定在代码里，
免得下一轮又有人（包括我自己）翻案重改。

# v2.21.0 · 暴击率与暴伤的三个病

服主：**「然后暴击率和爆伤你看看怎么修」**。

没给现象，我按数值反推——算了一遍满配可达到的量，问题自己浮出来了。

自检 399 → **402**。

---

## 一、先算：满配到底能叠到多少

暴击是**三方叠加**的 PDC 数（词条 + 宝石 + 剑灵），单看某一项都很正常，
叠起来才是灾难。取各项上限：

| 来源 | 暴击率 | 暴伤 |
| --- | --- | --- |
| 破绽词条（`crit_chance` 6%~22%） | 22% / 条 | — |
| 致命词条（`crit_damage` 25%~90%） | — | 90% / 条 |
| 星辉石 L5（base 0.04~0.09 × 5.0） | **45%** / 颗 | — |
| 破军石 L5（base 0.15~0.30 × 5.0） | — | **150%** / 颗 |
| 满配（2 词条 + 3 颗宝石，取上限） | **179%** | **+630%** |

对应战斗侧：

```java
if (critChance > 0 && ThreadLocalRandom.current().nextDouble() < critChance) {
    event.setDamage(event.getDamage() * (1.0 + critDamage));
}
```

`random < 1.79` **恒真** —— 满配就是「永久暴击」，一锤一锤全是暴击，
而玩家在 Lore 上看到的是「破绽 +22%」「星辉石 +45%」这种看起来很正常的数字，
**没有任何地方告诉他 179% 已经溢出了**。暴伤同理：×7.3。

---

## 二、三个病，不是三个笔误

### 病 1：没有上限，且溢出完全静默

暴击率超过 100% 之后，继续堆它的收益是**零**，但游戏不会告诉任何人。
玩家会一直堆，服主会一直收到「暴击是不是没生效」的反馈。

**修法**：`Crit.resolve(...)` 里压上限，配置 `combat.crit.max-chance`（默认 0.75）。
而且 `1.0` 是**硬天花板**——配置写 9.9 也只到 100%。「必定暴击」不该是一个可配置项。

### 病 2：倍率底数偏低，出现倒挂

原版跳跃暴击本身就是 **×1.5**。而自定义暴击是 `×(1 + 暴伤)`：

| 暴伤 | 旧倍率 | 原版跳劈 | 结果 |
| --- | --- | --- | --- |
| +25%（最低档词条） | ×1.25 | ×1.5 | **词条暴击不如随便跳一下砍** |
| +90% | ×1.90 | ×1.5 | 勉强强过 |
| +630% | ×7.30 | ×1.5 | 爆炸 |

最低档的词条是**倒挂**的，最高档是**爆炸**的，中间那段才是正常的。

**修法**：倍率改成 `底数 + 暴伤`，底数默认 1.5（原版值）。
于是 +25% → ×1.75（略强于跳劈，对得起一个词条位），+90% → ×2.4，
配上 `max-damage: 2.5` 上限 → 最高 ×4.0。

### 病 3：宝石和词条不是同一把尺子

| | 上限 |
| --- | --- |
| 星辉石 L5 暴击率 | **45%** |
| 破绽词条暴击率 | **22%** |
| 破军石 L5 暴伤 | **150%** |
| 致命词条暴伤 | **90%** |

一颗宝石顶两条词条。这不是"宝石更强"的设计意图，是两套数值分开调过、
没人把它们放在一张表里比。后果是**词条位失去意义**——玩家只会去堆宝石孔。

**修法**：宝石 base 区间下调到与词条同量级

| 宝石 | 旧 base | 新 base | L5 后 |
| --- | --- | --- | --- |
| 星辉石 | 0.04~0.09 | **0.015~0.030** | 7.5%~15% |
| 破军石 | 0.15~0.30 | **0.06~0.12** | 30%~60% |

**已镶嵌的宝石数值存在 PDC 里**（`GemType` 的老注释就写了这个性质），
所以老宝石保值，这次只影响新熔炼的。这意味着**上限是唯一能压住老存档的东西**——
这也是为什么病 1 必须修，光调数值没用。

## 三、修完之后的数

| 配置 | 暴击率 | 倍率 |
| --- | --- | --- |
| 单条破绽 + 单颗星辉 | 22% + 15% = 37% | 底数 ×1.5 |
| 加一条致命 + 一颗破军 | 37% | (1.5+0.9+0.6) = ×3.0 |
| 满配（2 词条 + 3 宝石） | 89% → **压到 75%** | 360% → **压到 +250%** = ×4.0 |
| 配置上限写 9.9 | **仍是 100%** | — |

满配仍然是强，但**有天花板，而且天花板是显式的**。

---

## 四、为什么做成纯函数

`Crit.resolve(...)` 是 `double × double → Profile`，不碰 Bukkit、不需要玩家。
理由和附魔那次一模一样：只要判定埋在 `CombatListener` 里（要造玩家才能跑），
这块就永远不会被自检覆盖——而它已经带着两个明显缺陷活到了 v2.21。

三条断言：

| # | 断言 |
| --- | --- |
| 1 | 179% → 压到 75% 且标记 capped；配置上限写 9.9 也不超过 100%；正常值 0.3 不被动；负数/NaN 归零 |
| 2 | 倍率 = 1.5 + 暴伤；暴伤 0.25 → ×1.75（不再弱于跳劈）；630% → 压到 ×4.0；底数被写成 0.2 时倍率不低于 1 |
| 3 | L5 星辉石 ≤ 20%、L5 破军石 ≤ 70%，且**三颗满级宝石的暴击率不足以顶满上限**（否则词条位没意义） |

第 3 条是这次最想留下的一条：它锁的不是某一个数，而是「宝石与词条的相对关系」。

## 五、第二次「加键忘了迁移」，这次是主动避开的

前两轮教训：**加配置键 → 同批加迁移步骤 → 抬 `CURRENT_VERSION`**，三件缺一就静默降级。

这次 `combat.crit.*` 三个键是 `step19CritKeys`，版本 9 → **10**，
落地后 `config check` 直接是 `✓ 必需键齐全（192 项）`，没有再报缺键。

和前几步不同的是，**这批键会改变行为**（封顶 + 抬底数），所以 step19 的日志措辞
单独写了：「注意这会让暴击率封顶 0.75、暴伤封顶 +2.5（原来是无限叠加）」。
「值等于代码默认、行为不变」这句话在这种迁移上是**不能写的**。

另外把暴击口径加进了 `/zhujian config check` 的「实际生效值」：
服主打开就能看到封顶到多少，不用去翻 config。

## 六、没动的（说明白）

- **跳跃暴击仍会叠加**：原版 ×1.5 在事件触发前就乘好了，我们的自定义暴击再乘一次。
  跳劈暴击 = 1.5 × 4.0 = 最高 6 倍。要消掉得去读客户端行为，做不干净，暂时留着。
- **弓/弩不触发自定义暴击**：监听的是 `EntityDamageByEntityEvent` 且 `damager` 必须是 `Player`，
  箭的 damager 是 `Arrow`。远程武器要另做一套。
- **护甲词条池没有暴击**（是 armor_plate/tough_plate/vitality/knockback_resist），
  所以「只读主手 PDC」目前是对的。哪天往护甲池里加暴击，这里就会变成死属性。

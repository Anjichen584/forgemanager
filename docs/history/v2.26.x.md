## 十五·一、v2.26.0 观测类三条 + 审计轮六修

### 这一轮加了什么（四件，都是「已有的数，终于看得见」）

| 功能 | 命令 | 底层 |
| --- | --- | --- |
| 战力曲线 | `/zhujian power log` | 新存档 `power-log.yml`（每人 12 条，10 分钟去重窗口） |
| 战力对比 | `/zhujian power compare <玩家>` | 纯只读，比双方主手 PDC |
| 历届赛果 | `/zhujian contest history [届次号]` | 新存档 `contest-history.yml`（保留 N 届） |
| 比试排行 | `rank duel` 第六维 | `Stats.duelWins/duelLosses` |
| 公开档案 | `/zhujian stats of <玩家>` | 白名单字段，不碰 ProfilePanel |

### 为什么 `power-log` 的定位写「观测数据，不是账本」

`PowerLogStore` 的类注释第一段就钉死了这件事。理由是同仓库最贵的教训的反面：

- **钱货时序**（v2.25.6~2.25.9 连修四轮）的共同形状是「货交了、盘没写」——
  因为那笔数据一旦丢就是玩家的资产。
- **评分曲线丢一条**只影响「趋势回看的第 7 个点」，不影响任何人的剑、币、名声。

所以 `append()` 落盘失败**不回滚内存**，只返回 false 让调用方提示一句。别照抄
`DailyStore` 那套「先占额度再发货」的样板 —— 那是给账本用的。

### 为什么 `contest-history` 反过来必须同步写

`ContestHistoryStore` 的落盘时机与 `power-log` 完全相反，注释里写了原因：
**赛果是单次不可再生事件**。契约状态漏一笔下一轮还能补，一届大赛结束就结束了；
异步冲刷（≤30 秒）内崩溃 = 那届档案永久丢失。所以结算点直接同步原子写、判返回值、失败打 SEVERE。

### 为什么 `rank duel` 的值是 `wins * 1000000 - losses`

两个量纲要隔离：胜场是主键，负场只在同胜场时做次级比较。把胜场乘一百万后，
「多赢一场」的权重（10⁶）远大于「负场最多差多少」，于是排序天然是「先比胜场、再比少输」。
同时 0 胜的玩家 `value <= 0`，被 `sorted()` 的 `metric.value(st) > 0` 挡在榜外 ——
这正好是压测 `duelRank` 阶段断言的「0 胜不占榜」。

### 赛季归档里的「生涯 vs 本赛季」（v2.26.0 补的口径声明）

`Metric.values()` 六个维度**不是同一种东西**：

| 维度 | `resetSeasonal()` 清？ | 口径 |
| --- | --- | --- |
| 剑币 / 声望 / 连锻 | 清 | 本赛季 |
| 专精 / 强化 / 比试 | **不清**（刻意） | 生涯累计 |

不清是设计：专精等级、历史最高强化、生涯胜负都是玩家攒了很久的东西，赛季结算清零 = 数据事故。
但 `seasons/season-N.yml` 里六个榜长得一模一样，读档案的人会把「第 N 季 比试榜」误读成
「第 N 季打了多少场」。修法不是改 `resetSeasonal`（那是事故），而是**把口径写进档案本身**：
`SeasonManager.end()` 现在多写一段 `calibers.<维度>.career = true/false`，
判定来源是新增的 `Metric.career()`（唯一真相，不抄硬编码列表）。

放在独立的 `calibers` 段而不是塞进 `rankings.<维度>` 下，是为了不弄脏「那一层的键 = 名次」的结构。

### 修 #3 时踩到的坑：只加清单是错的

`restore()` 的顺序是「flush 脏数据 → 前置备份 → 覆盖文件 → **只重载不保存**」。
只把新文件加进 `SAVE_FILES` 而不补 `reloadAllSilently`，回档后内存里还是新赛果，
下一次 `record()` 整份回写就把回档静默吞掉 —— 这正是 v2.23.1 修过的那个 P0 的同型。
所以两处都要补，自检也按**方法体**分别核（不是数整文件出现次数：清单 + 两处 swallow 凑够 3 次，
但漏掉 reload 那条同样能凑够 3 次 —— 那样断言就是假绿）。

### 压测里最难查的一类红：外生扣费（不是插件缺陷）

这一轮压测连红两次，两次都报「剑灵重抽」阶段扣费不守恒，两次都**不是插件缺陷**：

| 报错 | 差额 | 真相 |
| --- | --- | --- |
| `每日限拦截却扣了钱 — 197660 → 158128` | 39532 | 服务端日志 12:15:31：「巨龙的怒吼撕裂了夜空—— Conc24 交不上税，契约粉碎…剑币少了 39532」，**同一秒对 31 个 bot 全扣** |
| `重抽扣费不守恒 — 应扣 2000，实扣 41932` | 41932 | 41932 = 2000（重抽）+ 39932（龙税）。同一个原因 |

根因：`ContractManager.isTributeDue()` → `windowOpen()`，**按游戏内昼夜**判断「今晚该交税了」。
压测跑得久，总会跨过结算时刻，于是全服性的龙税同时落到每个已签契约的 bot 头上，
而阶段里的余额断言把外生扣费算成了自己的账。

两条教训：

1. **断言只对自己触发的那一笔负责。** 「余额变了 = 我这条命令扣的」这个假设在并发压测里
   根本不成立。判据要么精确到单价（差额恰好 = 2000），要么点名差额降级为 WARN，
   绝不能只看「变了没变」就判 FAIL —— 那会把别的系统的问题记到被测功能头上，比假绿更误导。
2. **治根要靠环境隔离，不是靠断言求饶。** 光加归因只是第二道防线；真正干净的做法是让
   外生事件在压测期间不发生 —— `gamerule doDaylightCycle false` + `time set day` 把世界钉在白天，
   交税窗口就永远不开。时间类玩法本来就不在这 17 个阶段的覆盖范围里，冻结不影响覆盖面。

顺带修掉的：`botCount` 记的是「打算跑几个」（`joinWithRetry` 失败会少 push，它照样是 32），
新增 `botCountAlive` 记真正连上的数量，两者任一不符即判失败。

### 想加速？先说三个「试过不行」的结论

改完代码想快速验证，会自然想「压测能不能快点」。这一轮把三条路都试了，记下来省下次的时间：

**1. 加指令间隔（每条 sleep 5 秒）—— 方向反了。**
实测一轮 3,186 条指令（2,767 条 bot 指令 + 419 条 RCON 操作），全站吞吐已经很慢（72.5 条/分钟，
平均 0.83 秒一条）。再加 5 秒间隔 = 3186 × 5 = **4.4 小时**，而且把并发压力抹平，
等于不再测并发。**加间隔只会更长，不会更稳。**

**2. 缩短固定 sleep —— 有效但收益只有约 5 分钟。**
48 处 `wait(N)` 改成 `settle(bot, N)`（静默检测：回执一到 + 250ms 无新消息就返回，
上限保持原值所以慢路径行为不变），12 处改成 `until(谓词, N)`（等 GUI 打开、等背包同步）。
64 分钟 → 约 59 分钟。**为什么省这么少**：短等待（300/400ms）被 `minMs` 兜住省不了，
只有长等待（1600→850）才有肉；剩下 41 处 `wait` 是轮询间隔和 RCON 往返，本来就该保留。

**3. 阶段内并发（32 个 bot 同时跑）—— 走不通，根因在服务端。**
直觉上「每个 bot 操作自己的账号」应该快 32 倍。实测：32 bot 同时上线后**阶段挂死 400 秒**，
日志里一条 RCON 回包都没有；减到 8 个仍然全超时。单测定位到：

```
一次并发发 8 条 RCON `list` → 只回 1 条响应，其余 7 条永不回包
```

**Minecraft 的 RCON 是串行收发的。** 而每个阶段都要走 RCON（`setCoins` / `coins` 全是），
所以阶段内并发必然把后面 31 个 bot 的查询全部堵死。这条路已撤销，结论写进代码注释。

> 顺带修掉一个真 bug：RCON 原来用 `pending.push` + `pending.shift` 做 FIFO 配对，
> 假设「响应顺序 = 请求顺序」。串行跑一直成立，**并发就错配** —— A 的余额读给 B。
> 现在按 request id 精确配对（Map），并加了单条超时：服务端不回包时宁可报错，
> 不要像刚才那样无声挂死 400 秒。这个问题只在并发下显形，正是因为试了并发才被发现。

### 所以加速只有一条路：减少重复

真正的浪费在 `duelRank`：**17.7 分钟 / 约 64 分钟（28%）**，而它每轮只用 2 个 bot 打一场，
却对 31 个 bot 各跑一遍 —— 29 次是重复验证同一件事。把那处收窄能省 17 分钟，
是「缩 sleep」收益的 3.4 倍。

配套加了 `run-stress.py --key`：只跑 5 个**守恒律**阶段（auction / bid / burst /
spiritReroll / contract），约 17 分钟。用于「改完代码快速确认没把核心并发面改坏」。
**它不是通过标准的替代品，发版前仍应跑一次全量。**

### 修 #2 时补的迁移

`config-version` 22 → **23**，新增 `step32ContestHistory`。
这步必须用 `existsOnDisk()` 而不是 `cfg.contains()`：`contains` 会顺着 jar 内 defaults 答「有」，
于是补键变成恒 no-op 死代码（step29 已经为同一个坑写过注释）。

### 三条「审计方法」的教训（比缺陷本身值钱）

1. **写钉子的人必须自己跑一遍。** 第 15 条：一条「会扫出 25 个写入点」的钉子，我没跑就交了。

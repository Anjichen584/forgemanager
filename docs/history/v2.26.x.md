## 十五·一、v2.26.0 观测类三条 + 审计轮六修

### 这一轮加了什么（四件，都是「已有的数，终于看得见」）

| 功能 | 命令 | 底层 |
| --- | --- | --- |
| 战力曲线 | `/zhujian power log` | 新存档 `power-log.yml`（每人 12 条，10 分钟去重窗口） |
| 战力对比 | `/zhujian power compare <玩家>` | 纯只读，比双方主手 PDC |
| 历届赛果 | `/zhujian contest history [届次号]` | 新存档 `contest-history.yml`（保留 N 届） |
| 比试排行 | `rank duel` 第六维 | `Stats.duelWins/duelLosses` |
| 公开档案 | `/zhujian stats of <玩家>` | 白名单字段，不碰 ProfilePanel |

### 为什么 `power-log` 的定位写「观测数据，不是账本」

`PowerLogStore` 的类注释第一段就钉死了这件事。理由是同仓库最贵的教训的反面：

- **钱货时序**（v2.25.6~2.25.9 连修四轮）的共同形状是「货交了、盘没写」——
  因为那笔数据一旦丢就是玩家的资产。
- **评分曲线丢一条**只影响「趋势回看的第 7 个点」，不影响任何人的剑、币、名声。

所以 `append()` 落盘失败**不回滚内存**，只返回 false 让调用方提示一句。别照抄
`DailyStore` 那套「先占额度再发货」的样板 —— 那是给账本用的。

### 为什么 `contest-history` 反过来必须同步写

`ContestHistoryStore` 的落盘时机与 `power-log` 完全相反，注释里写了原因：
**赛果是单次不可再生事件**。契约状态漏一笔下一轮还能补，一届大赛结束就结束了；
异步冲刷（≤30 秒）内崩溃 = 那届档案永久丢失。所以结算点直接同步原子写、判返回值、失败打 SEVERE。

### 为什么 `rank duel` 的值是 `wins * 1000000 - losses`

两个量纲要隔离：胜场是主键，负场只在同胜场时做次级比较。把胜场乘一百万后，
「多赢一场」的权重（10⁶）远大于「负场最多差多少」，于是排序天然是「先比胜场、再比少输」。
同时 0 胜的玩家 `value <= 0`，被 `sorted()` 的 `metric.value(st) > 0` 挡在榜外 ——
这正好是压测 `duelRank` 阶段断言的「0 胜不占榜」。

### 赛季归档里的「生涯 vs 本赛季」（v2.26.0 补的口径声明）

`Metric.values()` 六个维度**不是同一种东西**：

| 维度 | `resetSeasonal()` 清？ | 口径 |
| --- | --- | --- |
| 剑币 / 声望 / 连锻 | 清 | 本赛季 |
| 专精 / 强化 / 比试 | **不清**（刻意） | 生涯累计 |

不清是设计：专精等级、历史最高强化、生涯胜负都是玩家攒了很久的东西，赛季结算清零 = 数据事故。
但 `seasons/season-N.yml` 里六个榜长得一模一样，读档案的人会把「第 N 季 比试榜」误读成
「第 N 季打了多少场」。修法不是改 `resetSeasonal`（那是事故），而是**把口径写进档案本身**：
`SeasonManager.end()` 现在多写一段 `calibers.<维度>.career = true/false`，
判定来源是新增的 `Metric.career()`（唯一真相，不抄硬编码列表）。

放在独立的 `calibers` 段而不是塞进 `rankings.<维度>` 下，是为了不弄脏「那一层的键 = 名次」的结构。

### 修 #3 时踩到的坑：只加清单是错的

`restore()` 的顺序是「flush 脏数据 → 前置备份 → 覆盖文件 → **只重载不保存**」。
只把新文件加进 `SAVE_FILES` 而不补 `reloadAllSilently`，回档后内存里还是新赛果，
下一次 `record()` 整份回写就把回档静默吞掉 —— 这正是 v2.23.1 修过的那个 P0 的同型。
所以两处都要补，自检也按**方法体**分别核（不是数整文件出现次数：清单 + 两处 swallow 凑够 3 次，
但漏掉 reload 那条同样能凑够 3 次 —— 那样断言就是假绿）。

### 压测里最难查的一类红：外生扣费（不是插件缺陷）

这一轮压测连红两次，两次都报「剑灵重抽」阶段扣费不守恒，两次都**不是插件缺陷**：

| 报错 | 差额 | 真相 |
| --- | --- | --- |
| `每日限拦截却扣了钱 — 197660 → 158128` | 39532 | 服务端日志 12:15:31：「巨龙的怒吼撕裂了夜空—— Conc24 交不上税，契约粉碎…剑币少了 39532」，**同一秒对 31 个 bot 全扣** |
| `重抽扣费不守恒 — 应扣 2000，实扣 41932` | 41932 | 41932 = 2000（重抽）+ 39932（龙税）。同一个原因 |

根因：`ContractManager.isTributeDue()` → `windowOpen()`，**按游戏内昼夜**判断「今晚该交税了」。
压测跑得久，总会跨过结算时刻，于是全服性的龙税同时落到每个已签契约的 bot 头上，
而阶段里的余额断言把外生扣费算成了自己的账。

两条教训：

1. **断言只对自己触发的那一笔负责。** 「余额变了 = 我这条命令扣的」这个假设在并发压测里
   根本不成立。判据要么精确到单价（差额恰好 = 2000），要么点名差额降级为 WARN，
   绝不能只看「变了没变」就判 FAIL —— 那会把别的系统的问题记到被测功能头上，比假绿更误导。
2. **治根要靠环境隔离，不是靠断言求饶。** 光加归因只是第二道防线；真正干净的做法是让
   外生事件在压测期间不发生 —— `gamerule doDaylightCycle false` + `time set day` 把世界钉在白天，
   交税窗口就永远不开。时间类玩法本来就不在这 17 个阶段的覆盖范围里，冻结不影响覆盖面。

顺带修掉的：`botCount` 记的是「打算跑几个」（`joinWithRetry` 失败会少 push，它照样是 32），
新增 `botCountAlive` 记真正连上的数量，两者任一不符即判失败。

### 想加速？先说三个「试过不行」的结论

改完代码想快速验证，会自然想「压测能不能快点」。这一轮把三条路都试了，记下来省下次的时间：

**1. 加指令间隔（每条 sleep 5 秒）—— 方向反了。**
实测一轮 3,186 条指令（2,767 条 bot 指令 + 419 条 RCON 操作），全站吞吐已经很慢（72.5 条/分钟，
平均 0.83 秒一条）。再加 5 秒间隔 = 3186 × 5 = **4.4 小时**，而且把并发压力抹平，
等于不再测并发。**加间隔只会更长，不会更稳。**

**2. 缩短固定 sleep —— 有效但收益只有约 5 分钟。**
48 处 `wait(N)` 改成 `settle(bot, N)`（静默检测：回执一到 + 250ms 无新消息就返回，
上限保持原值所以慢路径行为不变），12 处改成 `until(谓词, N)`（等 GUI 打开、等背包同步）。
64 分钟 → 约 59 分钟。**为什么省这么少**：短等待（300/400ms）被 `minMs` 兜住省不了，
只有长等待（1600→850）才有肉；剩下 41 处 `wait` 是轮询间隔和 RCON 往返，本来就该保留。

**3. 阶段内并发（32 个 bot 同时跑）—— 走不通，根因在服务端。**
直觉上「每个 bot 操作自己的账号」应该快 32 倍。实测：32 bot 同时上线后**阶段挂死 400 秒**，
日志里一条 RCON 回包都没有；减到 8 个仍然全超时。单测定位到：

```
一次并发发 8 条 RCON `list` → 只回 1 条响应，其余 7 条永不回包
```

**Minecraft 的 RCON 是串行收发的。** 而每个阶段都要走 RCON（`setCoins` / `coins` 全是），
所以阶段内并发必然把后面 31 个 bot 的查询全部堵死。这条路已撤销，结论写进代码注释。

> 顺带修掉一个真 bug：RCON 原来用 `pending.push` + `pending.shift` 做 FIFO 配对，
> 假设「响应顺序 = 请求顺序」。串行跑一直成立，**并发就错配** —— A 的余额读给 B。
> 现在按 request id 精确配对（Map），并加了单条超时：服务端不回包时宁可报错，
> 不要像刚才那样无声挂死 400 秒。这个问题只在并发下显形，正是因为试了并发才被发现。

### 所以加速只有一条路：减少重复

真正的浪费在 `duelRank`：**17.7 分钟 / 约 64 分钟（28%）**，而它每轮只用 2 个 bot 打一场，
却对 31 个 bot 各跑一遍 —— 29 次是重复验证同一件事。把那处收窄能省 17 分钟，
是「缩 sleep」收益的 3.4 倍。

配套加了 `run-stress.py --key`：只跑 5 个**守恒律**阶段（auction / bid / burst /
spiritReroll / contract），约 17 分钟。用于「改完代码快速确认没把核心并发面改坏」。
**它不是通过标准的替代品，发版前仍应跑一次全量。**

### 第三轮遗留三条：修了两条，第三条是「不该修」

第三轮收尾时列了三条「低危、未动」的项。这一轮逐条查证，结论不完全一样 —— **有一条根本不该修**，
把它写清楚比强行「修掉」更有价值。

**① `bounty-data.yml` 是全仓唯一「有 reload 无 flush」的项 —— 修了。**
回档是三段：`flushAll`（内存落盘）→ 覆盖文件 → `reloadAllSilently`（按盘重建）。
它有 reload 但没有 flush，后果不是「回档没生效」而是更阴的：文件被换成旧的，
内存还是回档前那份 `claimed`，**下一次 `claim()` 的 `save()` 整份回写，把回档静默吞掉**。
与 v2.23.1 的 stats、v2.25 的 contract.yml 完全同型。补了 `public void flush()`，
并把 `save()` 的异常面从只 catch `IOException` 扩到也 catch `RuntimeException`
（YamlIo 可能抛 SecurityException / IllegalArgumentException，原来会冒到 claim 的玩家提示里）。

**② `HallShrine.origin` 字段缓存 —— 修了。**
`origin()` 是惰性加载 + 一次缓存，回档换了 `hall.yml` 它不知道，于是殿堂原点在回档后
到重启前一直指向旧坐标，而 `/zhujian hall set` 写回去的还是缓存值 —— 等于回档对这字段完全没生效。
补了 `public void reloadOrigin()`（清缓存 + 重读，**不碰展示任务**：回档流程最后会统一重摆，
这里顺手 stop() 反而让那次重摆落空）。
注意 `hall.yml` 只补了 reload、**没有**补 flush：它两次写（halloffame set 整份重写、
setOrigin 改 shrine 段）都是变更即写，没有内存脏窗口，加 flush 只会在回档日志里多一条
「什么都没做」的记录。这条差异写进了自检钉子，以后有人「为了表格整齐」去补它会被拦下来。

**③ `metrics-export-<stamp>.csv` 与 `papi-cache/` 没进备份 —— 不该修。**
查证后这两个都不是「该备份的存档」：

- `metrics-export-*.csv` 是**用户主动导出**的产物（`/zhujian metrics export`），
  源数据在 `metrics-<日期>.yml` 里，而那份已经备份了。回档后重新导一次即可，
  而且「回档把玩家以前导出的 CSV 也一起还原」反而奇怪 —— 它不是世界状态。
- `papi-cache/` 是运行时编译 PAPI 扩展类的**缓存目录**，进程启动时重建
  （`Files.createDirectories` + 现场 javac），删了自动重新生成，本质是临时产物。

把它们塞进 `SAVE_FILES` 会有实际坏处：备份体积被无上限的历史 CSV 撑大，
回档时去覆盖一个马上就重新编译的缓存目录属于纯粹的噪音。**正确做法是文档写清楚
「它们故意不在清单里，别再加」** —— 也就是这一节本身。已在 `LATEST.md` §2 里标注。

> 一个附带的方法论教训：这三条原本被一起写成「低危待办」。逐条查证后，
> 一条是**真缺口**（会静默吞掉回档）、一条是**显示问题**（回档后坐标停在旧值）、
> 一条**根本不该做**。把三者混在一个清单里，等于让「待办」这个词同时承担
> 「必须修」「可以修」「别修」三种含义 —— 而清单只写「低危」，下一个人就分不出来。

### 悬赏领赏补二次确认（v2.26.1）：不可逆操作不该一步到位

`/zhujian shangjin claim <序号>` 原来一步到底：门槛校验通过就 `setItemInMainHand(null)`，
**剑当场消失、不可撤销**，换回一笔悬赏小钱。

问题不在「有人会恶意利用」，在**误触的代价不对称**：触发条件只是「主手拿了一件达标的锻造品」，
而玩家整理背包、切剑、试新剑时主手恰好就是那把。手滑补一个数字回车，主属性最好的剑就没了。
换回来的钱通常远不值那把剑 —— 收益和代价差了三个数量级，这种操作必须有闸。

值得记的是**这不是新设计，是补齐**：全仓同类不可逆操作早就是两段式 ——
- `spirit reroll`：预览 + `confirm`，且用 PDC nonce 把确认绑到同一把剑（v2.25.1 修的 P1）
- `dissolve` / `talent reset`：`confirm`
- `strengthen strip`：不带序号只列词条和费用

**唯独悬赏是一步到位。** 所以这是一次「同型里漏了一个」的收口，不是加新机制。

实现上照 `SpiritManager` 的写法，但**没照抄 nonce 进 PDC**：锻造品没有唯一 id 键，
往剑 PDC 写 nonce 会改动玩家物品（且回退/复制时会跟着跑）。改成"指纹"方案：

```
指纹 = 品质 + 强化 + 锻阶 + 剑名 + 灵性
```

校验三处都对齐才放行：①这一轮真的预览过 ②还是同一条悬赏 ③**主手还是预览那把剑**。
第③条是关键 —— 没有它就能预览一把破剑、换成满属性的剑再 `confirm`，
而门槛是对"当前主手"做的，等于绕过预览。

指纹刻意**不用物品哈希**：哈希会把「修过一次耐久」也判成换剑，而耐久和领赏无关，
只会让正常操作莫名其妙失败。同属性的两把剑指纹相同 —— 那种情况下交哪把都符合预览描述，
不构成「被扣了没想到的剑」。

顺带两处细节：
- 预览分支返回**空串**，命令层必须判空再 `Msg.prefix`，否则玩家收到一条只有前缀的空消息。
- 退服要清待确认状态（`ForgeListener.onQuit` → `bounties().forgetPending`）。
  这是 `SpiritManager` v2.25.2 的原话教训：不清的话重登后 `confirm` 仍匹配旧预览，
  等于绕过「必须先看预览」这道闸。

自检钉子 `悬赏领赏必须是两段式` 守六处：签名带 confirm 位、收剑在预览分支**之后**、
换剑校验存在、用完摘状态、退服清理、命令层识别第 4 段 + Tab 补全。
做过变异测试：抹掉换剑校验后钉子立刻红并点名原因。

### 极限锻造与剑灵显形整模块移除（v2.26.1）：删掉两个「谁加的都不知道」的功能

提交信息里一个字都没提，事后既查不到动机、也查不到需求来源，只能靠 `git log -S` 反推。

#### 删掉的是什么

| 模块 | 用户看到的东西 | 代码位置 |
| --- | --- | --- |
| **极限锻造** | `/zhujian forge risk` 预设下一把剑：命中区缩窄、分数 +35%、每阶段 6% 炸剑 | `forge/RiskMode.java`（整类）+ `ForgeManager` / `ForgeSession` / `ForgeListener` / `StatsStore` |

两个模块都被写成了**外挂式**：核心类独立成包，只在 `ForgingMasterPlugin` 里存一个字段、

**整个功能能一刀切掉，不牵连主线**。删除涉及 17 个文件，其中 3 个是整文件删（`git rm`），
其余是删字段 / 删 case / 删统计维度。

#### 连带必须一起删的东西（这才是容易漏的部分）

删功能最容易犯的错是「删了主类，留了一堆只往它上面浇水的管子」。这次一起清掉的：

1. **统计链路** —— `riskMade` / `riskLost` 从 `StatsStore` → `MetricsData` → `MetricsSample` →
   `MetricsHistory` → `MetricsCsv` → `MetricsGui` → `MetricsService` 整条串删。
   特别处理的是 `breaks`（碎剑率）：它**唯一的数据源就是极限锻造炸剑**。功能没了它永远是 0，
   留着就是一个「永远显示 0%、看起来像没人碎过剑」的假指标 —— 假绿比红更坏，所以整条删掉，
   而不是留着等 0。注意 `StrengthenService` 里也有叫 `breaks` 的局部变量，那是强化模拟的
   概率数学，与统计无关，**不能动**。
2. **称号维度** —— `SpectrumService` / `TitleService` 的 `case "risk-made"` / `"risk-lost"`，
   以及 `config.yml` 里 `condition: { type: stat, key: risk-made, min: 100 }` 的 `risk-taker` 称号。
   留着的话这个称号**永远解锁不了**，且解锁条件指向一个不存在的 stat key。
3. **必需键清单** —— `REQUIRED_CONFIG_KEYS` 里 3 个 `risk.*`。**这条是自检逮出来的**：
   我们已把 `config.yml` 的 `risk:` 段删了、清单里的也删了，但部署的是旧 jar，
   自检报「内置 config.yml 缺 3 个必需键：[risk.enabled, risk.score-bonus-percent, risk.explode-chance]」。
   重新 `mvn package` + 重新部署后消失 —— 提醒：**自检读的是打进 jar 的那份 config.yml，不是源码目录**。
4. **PDC 键** —— `Keys.SPIRIT_DISPLAY` / `SPIRIT_DISPLAY_BONUS`。这里有个细节：
   删了 `public static NamespacedKey` 声明，还得删 `onEnable` 里的 `= new NamespacedKey(...)` 初始化，
   否则编译报「找不到符号」；删完还要检查 javadoc 里有没有 `{@link #SPIRIT_DISPLAY}` 悬挂引用
   （`BIG_SWORD_DISPLAY` 的注释里正好有一句）。
5. **一条变假的钉子** —— `SelfTestSuite` 原来断言「剑体放大实体不能误打成剑灵标记」：
   `require(!pdc.has(Keys.SPIRIT_DISPLAY, ...))`。键都删了，这个断言变成**恒真**（编译不过 → 改掉后恒真）。
   恒真的钉子 = 没有钉子，所以改成断言它真正想守的东西：实体必须带**自己的**键且类型正确。

#### 数字怎么变

这与 `AGENTS.md` 第 6 条「只许增不许减」冲突，处理方式是在规则下面写一行例外说明 ——
**不能悄悄改数字**，否则下一个人分不清「删功能」和「删安全网」。

#### 学到的一条

**功能不该混进「修 bug」的提交。** 这次两个模块都是在一个标题写着「全面查错 + 数值收敛」的

## 十五·四、v2.26.3 契约刷满的真因 + 自检系统性假绿

### 「多敲几次 join 圣物就满了」——真正漏的是 quit

v2.26.2 以为是「重复 join」，把守卫从 `r.joined && r.day > 1` 改成 `r.joined`。
玩家照样能刷满，因为真正的口子在**另一个方法**里：

```java
// 旧 quit()
store.remove(p.getUniqueId());        // 档案整个删掉
```

`RelicPool.offer(owned, ...)` 只排除**已持有**。档案被删 → 重签时 `owned` 是空的
→ 从 12 个圣物里重新抽 3 个。于是 `quit` → `join` → `quit` → `join` …… 无限重掷，
定向钓「凤凰灰」（稀有度 5、每个周目日免碎一次）几轮就能凑齐。

还有第二道口子叠在同一处：`join()` 用 `store.ensure()` 判在契，而 `ensure()` 会**建一个
`joined = true` 的空档**。所以首次 join 反而被判成「已签」、什么都不发（功能像坏的），
玩家一旦 quit 又变成「新玩家」。

三条一起改才成立：

| # | 改法 |
| --- | --- |
| ① | 判在契用**只读**的 `store.run()`，不用 `ensure()`（它有建档副作用） |
| ② | `quit` 不再清档，只翻 `joined = false`，同时清掉未领的 `pickPending` |
| ③ | 重签走「复活」分支，**继承原圣物池**，不再发三选一 |

`relicBonus()` 本来就带 `!r.joined` 判断，所以退契期间圣物自动失效、重签自动恢复，
不需要额外状态。**「退出契约」是退出循环，不是清空重抽**。

钉子形状要注意：`join` 里 `ensure()` 在「首次签约」分支上是**合法**的（那时确实要建档），
所以不能一句 `!body.contains("ensure(")` 了事——那会把正确写法判红。
改成：判在契那步必须是 `store.run(`，且 `ensure(` 不许出现在任何 `if (` 条件里。

### 附魔台整叠吞书

`EnchantService.apply` 末尾无条件 `gui.setItem(BOOK_SLOT, new ItemStack(AIR))`。
书格放 2 本以上时，点一次只结算 1 本的代价，却把整格清成空气——多余的附魔书凭空消失。
改为 `consumeOneBook()` 按件递减（`clone()` 后再改 amount，避免污染调用方引用）。

### 潜行右键铁砧开两次面板

`PlayerInteractEvent` 对一次右键会**分别**派发主手、副手两次（`getHand()` 不同）。
`ForgeListener.onInteract` 没过滤手位 → 主手取消一次、副手再走一遍，等于开两次面板
（取完剑立刻又弹出菜单）。加 `event.getHand() != EquipmentSlot.HAND` 直接返回。

### 最要紧的一条：22 条静态钉子是假绿

这是「派了人查、跑了自检、还是漏」的真正原因，比上面三个 bug 严重得多。

22 条「按源码形状断言」的钉子都长这样：

```java
java.io.File pkgRoot = findSourcePackageRoot();
if (pkgRoot == null) {
    return;      // ← 找不到就 return，等价于「通过」
}
```

`findSourcePackageRoot()` 靠「从服务器工作目录向上 6 层 + 兄弟目录」猜源码树。
v2.26.1 之前测试服在 `D:\IDEA\mc-plugins\ForgingMaster\testserver`，是仓库的兄弟目录，能摸到；
搬到 `D:\game\1.21.10server` 后**不同盘符树，永远找不到**。

结果：自检报 **539 项 / 通过 539**，其中 22 条一次都没执行过。
日志里明明躺着 12 行 `[selftest] 找不到源码树，跳过 XXX`，但没人看 INFO 行。

修法三层：

1. `-Dforgemaster.source-root=<仓库根>` 显式指定，优先于自动探测；
2. 找不到时打 **WARNING**（不是 INFO）明说「这些钉子是跳过，不是通过」；
3. `tools/selftest.py` 默认带上这个参数（`--source-root`，默认仓库根）。

修完后跳过数 **0**，22 条钉子真正执行——**第一次跑就抓出我自己写的断言过严**
（`join` 里那处 `ensure()` 被误伤），说明它是活的。

**变异测试验证**：把 `consumeOneBook` 改回「整格清 AIR」，钉子立刻红：
`✗ 附魔台不许整摞吞书 → apply 必须走 consumeOneBook 按件递减`。
改坏会红，才算在守。

### P0：契约的钱货时序（三条同源）

`settleDay` 发赏金到 StatsStore（独立存档）、自己只 markDirty 等 30 秒异步冲刷——窗口内崩溃，
盘上旧档 + 游标未推进 → 重启重放整场结算。`pickRelic` 同理（先清再发的单次消费结构，盘上必须立刻同步）。
修法都是低频路径补一次同步 `store.save()`。谱系/图鉴/行会委托的领奖是「先落已领再发钱」契约的残留：
save() 吞 IOException 只打 warning——写盘失败时「已领」只在内存，重启可重领。改为 save 返回 boolean
（谱系/图鉴）或走 saveChecked（行会），失败回滚「已领」标记并拒绝发放。

### P1：跨账本家族（7 处）

铸造的剑币**。全部收口 `wallet().give` / `giveTo`（离线用 giveTo）：剑冢复刻、秘境通关（顺带补了缺失的

周赛会长奖、大赛 top5、行会委托。

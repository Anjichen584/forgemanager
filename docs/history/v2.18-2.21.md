## 十五、v2.21.0：沉浸式强化、蜕变独立、剑体放大

服主三句话：

> 那个强化里的进化直接去掉，或者换到别处，我要沉浸式强化。
> 然后放大倍数直接加倍加倍再加倍。
> +99 我要他跟泰坦 mod 那种剑一样大。

三件事：**拆耦合**、**改曲线**、**加视觉**。自检 386 → **391**。

### 一、蜕变不再卡强化（这是「沉浸式」的关键）

以前锻到 +5 就会被拦住：

```
已到这一阶的强化上限 +5——先蜕变「精钢」才解锁 +6 以上。/zhujian evolve
```

也就是说，**强化每走五级就断一次**，被一个有独立界面、独立成功率、独立材料、
独立费用的系统拦住。这是手感断裂的根源——不是文案问题，是设计耦合。

现在依赖关系只剩**单向**：

| 方向 | 是否还成立 |
| --- | --- |
| 蜕变要求剑先锻到某等级 | ✅ 保留（蜕变的前提是有一把够强的剑） |
| 强化要求先蜕变 | ❌ **删除** |

强化上限只认品质（粗糙 +40 / 普通 +50 / 精良 +60 / 史诗 +72 / 传说 +86 / 神话 +99），
一路锻到底不会再被任何东西拦住。`pendingGate` 保留下来给蜕变界面自己展示
「下一阶在哪」，不再参与强化判定。

同时把蜕变的 5 个类从 `strengthen/` 和 `gui/` 搬到独立包 `com.forgemaster.evolve`：
现在 `strengthen/` 只剩 `StrengthenService` / `Charm` / `Talisman`，
不会再有「改强化顺手改到蜕变」这种事。

### 二、剑体放大：加倍、加倍、再加倍

> **⚠ v2.22.1 起已移除**：手上悬浮剑与护甲体型放大两个功能已按服主要求整体下线，本小节及下文第三~六小节仅作历史记录。成长曲线本身保留，现在只驱动**铁砧上的剑身**逐锤变大（砧上大小 = `anvil-forge.display.sword-scale` × 曲线倍数）。

强化等级越高，手里那把剑**看起来**越大。三个加倍点：

| 等级 | 倍数 |
| --- | --- |
| +20 以下 | 不放大（不挂牌） |
| +33 | ×2 |
| +66 | ×4 |
| +99 | **×8**（泰坦级） |

里程碑之间用**几何级数插值**，不是线性。原因是人的眼睛对尺寸是对数感知的：
从 1 放大到 2 是「明显大了一圈」，从 7 放大到 8 几乎看不出来。线性插值会让
+33 之后的每一级都「没感觉」，几何插值才能让每一段的手感一致。

配置：

```yaml
strengthen:
  big-sword:
    enabled: true
    min-level: 20            # 低于这个等级不挂牌（省性能，也避免刚强化两下就变大）
    milestones: [33, 66, 99] # 三个加倍点
    multiplier: 2.0          # 每个里程碑在上一个基础上乘这个数
    max-scale: 8.0
    update-ticks: 2
    per-player-toggle: true
    offset-forward: 0.55     # 挂手上往前伸多少格
    offset-right: 0.34       # 往右手侧偏多少格
    offset-down: 0.30        # 从视线高度往下落多少格
```

### 三、实现：复用已验证的 ItemDisplay 路子

不是换物品模型（那要玩家装资源包，而且 99 个等级要 99 个模型）。用的是
`ItemDisplay` 实体渲染一份放大的「影子剑」，每 2 tick 跟到手上——和
`spiritdisplay`（剑灵挂在肩侧）同一套技术，所以生命周期约定也照抄：

- 非持久实体（崩服 / 强杀不留档）
- PDC 标记认领（`big_sword_display`，**和剑灵的键分开**——共用一个键会导致
  「关掉剑灵把大剑一起撤了」）
- 启动时清扫孤儿
- 换世界 / 死亡 / 下线/ 取关 → 撤

位置用视线方向 + 水平右向量算，所以低头抬头转身时大剑都跟着手走，
不飘在身体中心。

### 四、三个诚实的取舍

**会看到两把剑。** 手里那把原版物品是客户端渲染的，服务端藏不掉，所以巨型模型是
套在原版剑外面的——视觉上像「一把大剑里嵌着小剑」。泰坦模组也是类似处理。
要做到只看到一把，必须上资源包。

**不跟挥砍动画。** 攻击时大剑不跟着挥。要跟得自己做摆动动画（读
`isSwingingArm()` 驱动），成本高，先不做。

**第一人称可能挡视野。** 所以有 `per-player-toggle`：玩家敲 `/zhujian bigsword`
自己关掉。这个偏好只存内存，重启恢复默认开——重置成「开」比永久留在「关」
更不容易让人以为功能坏了。

### 五、插件自己被自己的检查抓了一次

加完 `offset-forward/right/down` 三个键后实机跑 `/zhujian config check`：

```
✗ 缺 1 个必需键（缺键会静默用代码默认值，服主改不到）
· strengthen.big-sword.offset-forward
```

因为这三个键是 step17 写完之后才补的，而 `strengthen` 段在盘上已存在，
step15 的「整段缺失才补」不会碰它。补进 step17 后复查：**必需键齐全（188 项）**。

上一版做的检查工具，第一次派上用场就是抓我自己。

### 六、装备（护甲）也能变大

剑走 `ItemDisplay` 挂影子模型，护甲不能照抄——四件各有各的位置和朝向，
手写偏移永远会歪。所以护甲走另一条路：**`Attribute.SCALE` 整体缩放**。

装备与身体天然同步，走路挥手都跟着走，不会穿模。曲线按**穿戴护甲的平均强化等级**算：

| 护甲平均等级 | 体型 |
| --- | --- |
| +20 以下 | ×1.00 |
| +33 | ×1.10 |
| +66 | ×1.21 |
| +99 | ×1.33 |

上限 1.40，**不是 8 倍**——原因写在下面。

#### 为什么取平均而不是取最低

取最低等于「必须四件全练」：三件 +99、一件 +0 完全没有效果，手感很挫。
取平均让每一件的投入都算数。另外 `min-pieces: 2` 兜底，穿一件就变大会很怪。

#### 代价必须说清

`Attribute.SCALE` 会**同时改碰撞箱和视线高度**。大个子确实更容易被箭射中、
能站进更浅的台阶、头顶的判定也更高。这就是「泰坦体型」的一部分，
但它确实改变了战斗判定——所以上限只给到 1.40，而剑可以给到 8 倍（剑只是视觉，不参与判定）。

#### 和别人不打架

缩放修饰符挂在独立的 `NamespacedKey`（`player_scale`）上。别的插件也可能动 `SCALE`，
有键才能只摘自己那一条。自检里专门挂了一条「别人的」SCALE 修饰符，验证摘自己的时候
不会把别人的一起清掉。

`stop()` 时必须把修饰符摘掉——它跟着玩家档案走，不摘的话重载插件后玩家会永久变大。

### 七、懒人指令：`/zhujian givefull`

正常路径拿一件满配要经过**生成 → 强化 99 次 → 蜕变 6 阶 → 重铸词条 6 次 → 开孔 → 镶宝石**，
几十步且大量掷骰。做平衡测试、给主播演示、开服补偿都要用，每次手搓不现实。

```
/zhujian givefull <玩家> <剑胚|armor-剑胚-部位> [品质]     # 别名 maxitem / manpei
/zhujian givefull Steve iron                           # 默认神话
/zhujian givefull Steve armor-iron-chestplate mythic
```

一次给到：

| 维度 | 落到的值 | 走哪条路 |
| --- | --- | --- |
| 品质 / 评分 | 指定品质（默认神话）· 评分 100 | `ItemFactory.buildDirect` |
| 强化 | 该品质硬上限（神话 **+99**） | `StrengthenService.setLevel` |
| 蜕变 | 最高阶 **6 阶** | `EvolutionService.forceStage`（新增） |
| 词条 | 填到上限（默认 **6 条**），值取上限，按属性去重 | `Reforge.addAffixRaw` |
| 宝石 | 孔开满，每孔 **Lv.5**，数值取类型上限 × 等级倍率 | `GemService.fillMax`（新增） |

**关键设计：每一维都走真实的写入路径，不写死 Lore 文案。** 否则会造出
「Lore 显示造化六阶、属性乘区还是 0 阶」这种假货——那是最难查的一类 bug。
收尾统一 `strengthen().apply()` 一次，保证属性和显示一致。

为此新增了两个「管理用途」的入口，都在 javadoc 里写明绕过了什么：

- `EvolutionService.forceStage(item, stage)` —— 绕过成功率、材料、费用、赛季登记
- `GemService.fillMax(item, sockets, grade)` —— 绕过扣费与掷命中

它们不是给玩家用的，所以不放进任何 GUI。

### 八、插件第二次被自己的检查抓住

加完护甲缩放的 5 个配置键后，实机 `/zhujian config check`：

```
✗ 缺 1 个必需键（缺键会静默用代码默认值，服主改不到）
· strengthen.big-sword.player-scale.enabled
```

**这次的原因和上次不一样，更值得记**：盘上 `config-version` 已经是 8，
而 step17 只在版本号跨过阈值时跑一次——已经升到 8 的服务器**永远不会再跑 step17**。

所以迁移的版本号是**一次性闸门**，每加一批键就必须再抬一次版本号。这一批单独做成
`step18PlayerScaleKeys`，`CURRENT_VERSION` 8 → **9**。复查：**必需键齐全（189 项）**。

同一类 bug 两次都是检查器抓的，不是人看出来的。

### 十、暴击率与暴伤：三个病

#### 先算一遍满配

暴击是**三方叠加**（词条 + 宝石 + 剑灵），单看每项都正常，叠起来就炸：

| 来源 | 暴击率 | 暴伤 |
| --- | --- | --- |
| 破绽词条 | 上限 22% | — |
| 致命词条 | — | 上限 90% |
| 星辉石 L5 | **上限 45%** | — |
| 破军石 L5 | — | **上限 150%** |
| **满配** | **179%** | **+630%** |

而战斗侧是 `random < critChance`，`random < 1.79` **恒真** —— 满配就是永久暴击，
Lore 上却只写着「破绽 +22%」「星辉石 +45%」这种看着很正常的数字，**溢出完全静默**。

#### 病 1：没有上限

**修法**：`combat.crit.max-chance` 默认 0.75，且 `1.0` 是硬天花板——
配置写 9.9 也只到 100%。「必定暴击」不该是可配置项。

#### 病 2：倍率底数偏低，出现倒挂

原版跳跃暴击就是 ×1.5，而自定义暴击是 `×(1 + 暴伤)`：

| 暴伤 | 旧倍率 | 原版跳劈 |
| --- | --- | --- |
| +25%（最低档） | ×1.25 | ×1.5 → **词条暴击不如跳一下砍** |
| +630%（满配） | ×7.30 | ×1.5 → 爆炸 |

最低档倒挂、最高档爆炸，只有中间那段正常。

**修法**：倍率改成 `底数 + 暴伤`，底数 1.5（原版值）。+25% → ×1.75，+90% → ×2.4，
配 `max-damage: 2.5` 上限 → 最高 ×4.0。

#### 病 3：宝石和词条不是同一把尺子

一颗星辉石 L5（45%）顶两条破绽词条（22%），一颗破军石（150%）顶 1.7 条致命词条（90%）。
不是"宝石更强"的设计，是两套数值分开调过、没人放在一张表里比——
后果是**词条位失去意义**，玩家只会去堆宝石孔。

**修法**：星辉石 base 0.04~0.09 → **0.015~0.030**（L5 = 15%），
破军石 0.15~0.30 → **0.06~0.12**（L5 = 60%）。

已镶嵌的宝石数值存在 PDC 里，所以老宝石保值——**这也是为什么病 1 必须修，
光调数值压不住老存档**。

#### 修完的数

| 配置 | 暴击率 | 倍率 |
| --- | --- | --- |
| 单条破绽 + 单颗星辉 | 37% | ×1.5 底数 |
| 再加一条致命 + 一颗破军 | 37% | ×3.0 |
| 满配 | 89% → **压到 75%** | 360% → **压到 250%** = ×4.0 |

满配仍然强，但有天花板，而且天花板是**显式**的——`/zhujian config check` 里直接能看到：

```
├ 暴击口径: 暴击率上限 75% · 暴伤上限 +250% → 最高 ×4.00（倍率底数 ×1.50）
```

### 十一、词条乱到胸甲上出暴击率

**不是「全局生效」，它在胸甲上是死属性。** `CombatListener` 只读主手 PDC，
护甲上的暴击率写进 PDC、写进 Lore，然后没有任何代码读它。

顺着查牵出三个病：

| # | 病 | 影响 |
| --- | --- | --- |
| 1 | `buildDirect` 给护甲用淬火池（全攻击向） | 胸甲出暴击率/吸血/火焰 |
| 2 | `pick()` 抽不满就回退**整张词条表** | 剑上出「护甲值」，护甲出攻击词条 |
| 3 | 护甲词条 modifier 键不带部位 | **同一词条出在两件护甲上，只有一件生效** |

#### 三条写入路径，只有一条错

正常锻造走 `pickStrict(ARMOR_AFFIX_POOL)`（对），重铸走 `reforge.armor-pool`（对），
而 `buildDirect`——`/zhujian give` 和 `givefull` 的公共路径——无条件用 `quench.pool()`。
油淬池是 `[attack_damage, crit_chance]`，护甲走这条路必然出暴击率。

#### 剑抽到防御词条，伤害更大

`pick()` 在池子抽不满时回退到**整张表**。淬火池只有 2~3 条，精良以上要 4~6 条：

| 淬火 | 池深 | 精良要 | 从全表捞 |
| --- | --- | --- | --- |
| 水淬 | 2 | 4 | 2 条（可能是护甲值、生命上限） |
| 冰淬 | 3 | 6 | 3 条 |

**剑上会出「护甲值」**——白瞎一个词条位。加了 `WEAPON_AFFIX_POOL`（13 条减 5 条防御 = 8 条），
兜底只在武器向里补。

#### 护甲词条撞键：v2.10 起就没生效过

`fm_armor_plate` 不带部位，而护甲一次穿四件——两件都 roll 到「护甲值」时键相同，
原版按键去重，**后面那件直接失效**。Lore 上两件都写着 +1.4，实际只算一件。

一直没被发现，是因为那条「四件穿一起不会互相顶掉」的断言只检查 `Attribute.ARMOR`，
而护甲上原本全是攻击词条（病 1），压根没有护甲属性词条参与检查。**两个 bug 互相掩护。**

修法：新物品键改成 `fm_<词条>_<部位>`；`rebalanceArmor` 里加迁移把老物品原地改名
（数值不动）；`ARMOR_REBALANCE_VERSION` 1 → 2 让老装备再跑一遍。

#### 收口，不再靠「每个调用点都记得」

`buildDirect` 这个 bug 活了一整年，说明「各自选对池子」不可靠。所以在
`ItemFactory` 真正写 PDC 的那个点加守卫：护甲上非防御词条一律丢弃并告警。

位置很讲究——必须在**暴击/吸血/火焰累加之前**。第一版插在累加之后，
词条摘掉了但 `crit += value` 已经算过，PDC 里的数值照样留着。

### 十二、自检新增 14 条

1. 曲线三个加倍点：+33 ×2、+66 ×4、+99 ×8
2. 起点与单调性：+20 以下恒为 ×1，0~99 逐点不减、不超上限
3. 配置容错：乱序/重复/负数里程碑被排序去重，`multiplier≤1` 与 `NaN` 不产生无限大
4. 线上配置读得出曲线且描述含三个加倍点
5. **挂载链路**：造一把 +40 的剑 → 生成 ItemDisplay → 读回缩放与 PDC 标记，
   并断言它没被打成剑灵的标记
6. **护甲缩放**：SCALE 修饰符能按 NamespacedKey 精确摘掉；挂一条「别人的」修饰符，
   验证摘自己的时候不会连累它；护甲 +99 的体型算得出 1.331
7. **满配四维**：强化拉满、蜕变压到最高阶（且〔铭牌〕真打上）、宝石孔开满且全 Lv.5、
   词条上限可读且大于 0
8. **暴击率封顶**：179% → 75%；配置写 9.9 也不超 100%；正常值不被动；负数/NaN 归零
9. **暴伤底数**：倍率 = 1.5 + 暴伤；+25% → ×1.75（不再弱于跳劈）；630% → ×4.0
10. **宝石与词条同量级**：L5 星辉石 ≤ 20%、L5 破军石 ≤ 70%，
    且三颗满级宝石的暴击率不足以顶满上限（否则词条位没意义）
11. **词条池不越界**：浅池（2 条）+ 要 6 条 → 只用武器池补，不漏防御词条、不出重复
12. **胸甲不出暴击**：`buildDirect` 连造 6 件，词条全在防御池，CRIT_CHANCE / LIFESTEAL 都是 0
13. **剑不出防御词条**：连造 6 把，词条全部不在防御池
14. **护甲词条键按部位分开**：两件都挂「护甲值」→ 一个 `_chestplate`、一个 `_leggings`

第 5 条是这版最值钱的一条：纯函数对不代表链路对，它把
`SwordScale` / `Service` / `Keys` / 实体 PDC 四段焊在一起验。

## 十六、v2.20.0：经济流水与服主数据看板（切片 1）

到 v2.19.2 为止，这个仓库里所有关于经济的结论都是**推演出来的**：
「打一把剑赚 102 剑币」「强化 +40 要约 62 把剑」「蜕变六阶总共 89,105 剑币」。
这些数字来自静态配置 + 马尔可夫链，是**模型值**。

真实服务器上产出与消耗是什么形状、哪个模块在吸币、玩家是不是在囤币——
一个数字都看不到。这一版补的就是这个缺口。

自检 383 → **386** 全绿。规划见 [`audit/08-expansion-plan.md`](../../audit/08-expansion-plan.md)。

### 一、地基：给每一枚剑币记上理由

钱原来只有两个动作（加 / 扣），没有来路和去向。`StatsStore` 新增计数，
但**只在原有的三个收口点记账**，不散改：

```java
public long addCoins(UUID id, long amount);                          // 默认 OTHER_IN
public long addCoins(UUID id, long amount, CoinReason reason);       // 记流水
public boolean takeCoins(UUID id, long amount);                      // 默认 OTHER_OUT
public boolean takeCoins(UUID id, long amount, CoinReason reason);
```

旧调用点一行不用改（落进「其它」桶），需要精确的地方传理由。
`Wallet.take/give` 同样加了理由重载，所以宝石台、黑市这些走钱包的消费也能归类。

代价很低的原因：**剑币增减本来就只有三处**（`StatsStore:396` 加、`:410` 扣、
`:422` 赛季清零），全仓库没有第四处绕过。这一点是这轮能低成本落地的前提。

`CoinReason` 是**粗桶枚举**（先粗后细，细化只加枚举值、调用点不返工）：

| 方向 | 桶 |
| --- | --- |
| 产出 | 锻造奖励 · 委托交货 · 大赛名次 · 拍卖成交 · 每日签到 · 悬赏 · 剑冢挑战 · 成就奖励 · 师徒分成 · 通行证奖励 · 图鉴名谱 · 龙税贡品 · 退款回滚 · 其它产出 |
| 消耗 | 商会采购 · 强化费 · 蜕变费 · 宝石台 · 重铸费 · 词条符 · 剑魄分解 · 拍卖抽成 · 拍卖买入 · 黑市 · 剑冢费用 · 行会 · 其它消耗 |

落盘键是 `key()`（`forge` / `gem` …）而不是枚举名，常量改名不会让历史快照失配。

### 二、两个刻意的口径

**「拍卖买入」记成消耗，不是中性转移。**
买家侧记 `auction-buy`、卖家侧记 `auction`，两行之差正好是被系统吃掉的抽成——
并排看就能直接读出抽成率。若把买家付款归进「其它消耗」，这笔会淹在噪声里。

**退款回滚单列，并从产出总额里剔除。**
不剔的话，一块钱转两圈就能刷出假通胀。报表里它单独一行，不参与净通胀计算。

### 三、基尼系数：小样本必须闭嘴

第一版直接对全服算基尼。实测：

```
剑币总量: 300 · 人均 8 · 中位 0
基尼系数: 0.97 偏高
```

33 个档案里只有 1 个人有 300 币。数字数学上没错，可那 32 个零余额档案是
「没玩过」或「赛季重置后还没上线」，不是「被经济排斥的穷人」——
**拿死亡档案衡量贫富差距**，结果就是告警天天挂着变背景噪音。

改了两处：

1. 基尼只在**持币玩家**（余额 > 0）上算，并如实写清排除了多少人
2. 持币玩家少于 5 人时直接显示「样本太少，暂不下结论」，不给红字

现在的输出：

```
├ 基尼系数: 样本太少（1/5 人），暂不下结论 (按 1 名持币玩家算，36 人零余额已排除)
```

中位数保留**全体口径**——「中间那个玩家有多少钱」本身就是要看的东西，
中位 0 配人均 8，正好说明大多数人手里没币。

### 五、顺手逮到的两个真实问题

**`Msg.fmt` 跟着 JVM 的 locale 走。** 德语 / 法语区的服务器上小数点是逗号，
「63.9%」会渲染成「63,9%」——而玩家看到的百分比、倍率表格到处都是这个函数
渲染出来的。已锁死 `Locale.ROOT`。

**附魔镶孔扣了钱读不出 meta 就直接 return。** 同流程的「取回」分支早就有
`REFUND` 兜底，镶孔这里漏了：玩家白付一次 300 剑币，物品还是原样。
已补退款并提示。

### 六、自检新增 3 条

1. **经济流水恒等**：余额 == 初始 + 产出 − 消耗，且四个分桶金额对得上
2. **扣款失败不记流水**：钱不够时消耗计数不变（防止「记账成功但没扣到钱」的假账）
3. **看板配置合法**：`top-n` 在 1~50、`gini-warn` 在 0~1

### 七、一个只有全绿测试抓不到的问题

4 路并行按**目录**分域，合并后编译通过、386 条断言全绿。然后扫了一遍裸调用：

```bash
grep -rn 'takeCoins(\|addCoins(' | grep -v CoinReason
```

抓出 6 处没人认领的：`growth/AchievementEvaluator`（成就发钱）、
`order/OrderService`（发单托管）、`spirit/SpiritManager`（剑灵费）、
`tombrun/TombRunService`（秘境门票），加上命令层 2 处。

**测试全绿却漏了它们**，因为带默认值的旧签名让漏掉的调用点照样编译、照样运行，
只是数据落进「其它」桶——功能不坏、断言不红、日志不响，只是报表上「其它消耗」
莫名占 40%，而服主永远不知道那 40% 是什么。

教训：按目录分域会漏掉没人认领的目录。更稳的分法是**先 grep 出全部调用点，
再按调用点清单分工**。已全部补上，并把「其它桶占比」本身当成指标——占比异常高
就说明还有地方没接上。

## 十七、v2.19.2：配置漂移、黑市空货架与蜕变重排

这轮换了更硬的切入方式：不靠读代码找味道，而是**把「代码读的键」和「盘上有的键」做机器比对**。
结果比预期严重得多——老服的 config.yml 里，**整整 13 个配置段从来不存在**。

自检 378 → **383** 全绿。完整推导见 [`audit/07-round2-2.19.2.md`](../../audit/07-round2-2.19.2.md)。

### 一、最重的一条：黑市货架永远是空的

拿内置 `config.yml` 的全部节点跟测试服盘上的比：

```
资源里 1374 个节点，盘上缺 187 个
整段缺失：blackmarket  codex   daily    dissolve  guild      hall
          order        placeholder  relic-set  season-pass  spectrum
          titles       tombrun
```

大部分段代码里都有兜底（`getInt("x.y", 默认值)` 天然容错），**黑市是例外**：

```java
// BlackmarketService.pool() —— getMapList 没有默认值重载
for (Map<?, ?> raw : plugin.getConfig().getMapList("blackmarket.pool")) { ... }

// BlackmarketService.offers()
if (pool.isEmpty()) return out;   // ← 盘上没这段 = 空列表 = 空货架
```

玩家打开黑市：界面正常、价格区正常渲染、**一件货都没有**，日志一声不响。

旧迁移为什么没管：它们全是「补某个标量键」，`putIfAbsent` 只认点号路径。
只要 config.yml 生成得早，后来新加的功能段就永远进不去。

修法是 **step15 整块自愈**，原则极保守——**只补「盘上完全没有」的东西，
段里只要有一个键存在就整段不碰**：

```java
for (String path : res.getKeys(true)) {     // 遍历内置资源
    if (disk.contains(path)) continue;      // 盘上有 → 服主在管
    if (祖先已整块补过) continue;            // 最浅节点优先
    if (是段) 拷所有叶子并记为 coveredBy;
    else      cfg.set(path, res.get(path));  // 标量 / 列表都要认
}
```

三个踩过的坑：`titles` 是**顶层列表**（第一版只认 `ConfigurationSection`，补了 0 个键）；
`mentor.graduation` 这类**层内子段**要整块补而不是逐个叶子；纯空段要 `createSection`。

实测（测试服 5 → 6）：补回 14 处 / 41 键，复查**盘上缺 0 个节点**。

### 二、双账本：为什么会有两个钱包

插件里其实一直是两本账，只是以前没写清楚：

- **剑币**（`StatsStore`）：插件自己的硬通货。锻造奖励、委托、大赛、拍卖、强化、蜕变、
  商店、词条、剑冢、行会——**全部记在这本**。
- **服务器经济**（`EconomyBridge`：Vault / CMI / 内置兜底）：**只有锻造费**走它。

2.18 那一批新模块（宝石 / 黑市 / 签到 / 重铸）直接调了 `EconomyBridge`。装了 Vault 的服上，
玩家锻造赚剑币、镶宝石扣金币——两本账谁都花不出去。测试服正好是 Vault + CMI，
所以这个 bug 一直在，但自检只验了 `plugin.economy() != null`，没验「谁扣哪本账」。

现在全部收口到 `com.forgemaster.econ.Wallet`：

```java
Wallet w = plugin.wallet();
w.coins(player);          // 按当前口径读同一本账
w.take(player, 200);      // 扣；不足返回 false
w.give(player, 200);      // 退费走同一本账（防「扣金币退剑币」凭空造币）
w.format(200);            // 金额文案跟着口径走
```

配 `economy.coin-sinks` 一个开关：

```yaml
economy:
  coin-sinks: plugin    # plugin（默认，按 README 走剑币） / server（改扣 Vault）
```

没装 Vault / CMI 时两条路完全等价（`COINS` 后端本身就是 `StatsStore`），单人服无感。

`/zhujian money` 现在把两本账并排打出来，服主一眼能判断口径有没有配错：

```
你的余额：1,024.00 金币（Vault）
```

#### 哪些扣费跟 `coin-sinks` 走，哪些永远走剑币（v2.25.4 摸底）

「收口到 Wallet」这句话容易被读成「所有扣费都跟开关走」，其实不是。这轮压测前把全仓
`takeCoins` / `wallet().take` 的调用点逐个点了一遍，实际是三类，别混：

| 类 | 走哪本账 | 调用点 |
| --- | --- | --- |
| **A. 跟 `coin-sinks` 走**（`Wallet`） | `plugin` → 剑币；`server` → Vault | 商会 `ShopManager`、黑市、签到、重铸、拍卖（冻结/退款）、订单托管 `OrderService`、行会基金 `GuildService`、声望兑换 `redeem`、秘境门票、剑灵喂养、强化**保险费** |
| **B. 永远剑币**（`stats().takeCoins`） | 恒为 `StatsStore.coins` | **强化本体**（`StrengthenService:1301`）、**蜕变**（`EvolutionService:182`）、**词条剥离 / 移植 / 合成**（`Imprint:174/265/425`）—— 这三处是锻造族，代码里写明「剑币 ≠ 服务器金币」 |
| **C. 永远服务器经济** | 恒为 `EconomyBridge` | **锻造费**（`README` 写明的唯一例外） |

判定标准不是「谁写的晚」，而是**这笔钱玩家是怎么赚的**：强化/蜕变/词条的费用是「锻一把赚回来的剑币」，
所以恒走剑币；商店/拍卖/行会那种「玩家之间流通的钱」才跟服务器经济走，否则服主的 Vault 会被架空的。

> 踩过的坑（v2.25.4）：一开始把 `Imprint` 的三处当成「漏收口」，改成 `wallet().take` 还写了注释。
> 再看 `StrengthenService:1260` 的 P1 注释才发现强化本体**是故意**走剑币的 —— 改了等于给
> `coin-sinks: server` 的服凭空换一套收费标准。已回退。**先看别处为什么这么写，再判是不是 bug。**

### 三、主线程写盘：两处「每锻一把就整档重写」

### 四、强化模拟器：从「骗人」到「说实话」

旧实现把所有「失败且没碎」都当成降 1 级：

```java
visit[L][L - 1] -= q * (1.0 - b);   // 错：没看门票怎么分
```

而真实掷骰是五态：失败里 `damage-share` 那一半才降级，另一半是**空锤**（原地不动）；
成功里还切出一块 `greatBase 0.08` 是**大成 +2 级**。旧算法既没算空锤缓冲，也没算大成加速，
高段被判成强负漂移，期望值指数爆炸。

现在按 `odds()` 的同一套概率建马尔可夫链，逐级算
`pSucc / pGreat / pDamage / pHold`，解两个线性方程组（期望访问次数、达成概率），
碎裂是吸收态。发散段返回 `-1` 哨兵，输出改成人话：

```
这一段期望不收敛：成功率已经低于损伤回流，硬锤只会越锤越低。
要么靠 连击 攒无损、要么上 护胚符 / 稳胚符，别指望蛮力堆。
（模拟器只算裸锤，不把连击 / 炉火 / 符算进期望）
```

自检里直接钉了口径一致性：五态和为 1、大成 = `greatBase`、成功+大成 = `successChance`、
损伤 = 非碎失败 × `damage-share`，四个等级档逐条核。

### 五、高段曲线：`+99` 以前是画出来的

用修好的模拟器（裸锤、不含连击/符）算「一次锻造成活到目标」的概率：

| 目标 | 旧曲线 | 折成「把剑」 | 新曲线 | 折成「把剑」 |
| --- | --- | --- | --- | --- |
| +40 ROUGH | 24.74% | 4 | 42.89% | 2 |
| +50 COMMON | 6.43% | 16 | 20.12% | 5 |
| +60 FINE | 0.72% | 139 | 5.94% | 17 |
| +72 EPIC | 0.0112% | 8,964 | 0.5494% | 182 |
| +86 LEGENDARY | 4e-8 | 1,866 万 | 0.0051% | 19,424 |
| +99 MYTHIC | 5e-10 | **5,381 亿** | 仍靠符 | — |

碎裂风险在几百锤里复利，任何非零碎率都会把达成率稀释成 0——**配置写着 +99，
实际 +72 就封顶了**。

step12 迁移（`config-version` 2 → 3）只动四个数，判定沿用老规矩
（几个键**同时**等于旧默认值才整体换新，服主调过一个字不动）：

| 键 | 旧 | 新 |
| --- | --- | --- |

### 六、新模块：`/zhujian strengthen curve`

```
+40 · 期望 42 锤 · 6,336 剑币 · 达成 42.886%
```

### 七、自检：换掉 1 条错的，新增 6 条

**换掉的**：`期望次数大于 1/p（降级要重付）`。这条断言的前提本身是错的——旧模拟器
把所有非碎失败都当降级，所以「期望 ≥ 1/p 和」才成立；五态口径里大成是 +2 级、
空锤不降级，裸锤期望**必然低于** 1/p 和。现在改成两边界：
`一锤最多两级` ≤ 期望 < `1/p 和`。

**新增的 6 条**：

1. 模拟器与明牌抽票用同一套概率（五态和 = 1、大成 = `greatBase`、成功+大成 = 成功率、损伤 = 非碎失败 × `damage-share`）
2. 模拟器算出的期望消耗与逐级费用自洽
3. 消费口径统一：剑币账户只有一本账
4. 宝石 / 黑市 / 签到 / 重铸 不再直连 Vault
5. 结案只能成功一次（防二次给卖家打款）
6. 强化曲线表：六档各一行、不是锻造品给红字

另外补了个诊断钩子：**失败项现在会写进服务器日志**（`[SelfTest] ✗ 分组 / 项名 → 原因`）。
以前只发到聊天栏，项数一多 RCON 回包会被截断，`RESULT-selftest-*.txt` 里常常只剩

最终结果：**378 项，378 通过，0 失败**（连跑两次一致）。

## 十九、v2.19.0：收尾双工序（抛光 / 嵌银丝）

锻造从五段变七段：**开刃之后、淬火之前**插了两道冷加工收尾。原来开刃一结束就直接进淬火，
玩家在高档位上最大的感觉是「几下就完了」——档位越高越难，但流程反而更短。两道收尾把这段时间填回来，
而且都是「手稳就满分、手飘就掉分」的可练型。

### 一、两道工序怎么玩

| 工序 | 界面 | 操作 | 成色口径 |
| --- | --- | --- | --- |
| 抛光 | 一条 0~100 的光泽标尺 + 亮区 + 「下刀」键 | 指针往返扫，扫进亮区时下刀，共 3 刀（每刀后亮区重抽位置） | 偏差 ≤ 半宽一半 = 1.0；到两倍半宽 = 0；中间线性 |
| 嵌银丝 | 9 格银丝轨道 + 亮窗倒计时条 | 银丝逐根亮起，在亮窗内点中那一格；点错不推进但亮窗 −3 tick | 命中率 − 失手 × 0.05，夹 0~1 |

两道都吃**材料档位**：档位越高，抛光指针越快、亮区越窄、银丝亮窗越短、根数越多。星陨是硬门槛，
不是「多按几下」能糊过去的。

### 二、权重与打分口径

```
总评分 = (加热×20 + 锻打×35 + 叠钢×20 + 开刃×10 + 抛光×8 + 嵌银丝×7 + 淬火×(0~15)) ÷ 总权重 × 100
```

关键改动是**把「关工序」从硬编码摊派改成归一化**：2.18 及以前关掉叠钢/开刃时权重是手工摊给加热与锻打的，
每加一道工序都得重配一遍系数，还容易出现「关一道之后满分变成 97」。现在只把关掉的那道从权重总和里摘掉，
剩下的按占比重新归一——七工序满配 100、关任意组合仍是 100、全 0 仍是 0，以后再加工序不必配平。

- `ForgeManager.weightedScore(...)` 保留 7 参重载，语义等价于「抛光 / 嵌银丝这道工序不存在」，
  所以旧调用点的结果与 2.18 逐点一致（自检里直接钉了这条等价）。
- 「全流程无失手多给 1 词条」的判定同样接上两道工序：开着就必须 ≥0.99 才算无失手。

### 三、参数与配置

`config.yml` 新增 10 个键（`settings` 7 个 + `difficulty` 3 个），全部带中文注释：

```yaml
settings:
  polishing-enabled: true      # 抛光开关
  polishing-passes: 3          # 下几刀（1~6）
  polishing-speed: 2.6         # 指针每 tick 扫几点（0.6~8.0）
  polishing-window: 16.0       # 亮区半宽（4.0~40.0）
  inlay-enabled: true          # 嵌银丝开关
  inlay-window-ticks: 14       # 单根亮窗时长（5~40）
  inlay-length: 3              # 银丝基础根数（2~8，实际还随档位 +1）

difficulty:
  polish-speed-per-tier: 0.16  # 每高一档，抛光指针 +16%
  polish-window-per-tier: 0.09 # 每高一档，抛光亮区 −9%（最低 55%）
  inlay-window-per-tier: 0.10  # 每高一档，银丝亮窗 −10%（最低 50%）
```

**老盘自动补键**：`ConfigMigrations` 加了 step11，`config-version` 1 → 2。只写盘上**确实没有**的键
（判定读的是落盘那份 config.yml 的独立副本，不吃 jar 内的 defaults），服主自己加过、调过的值一个字不动；
插进去的值就是出厂默认，所以补键本身不改变任何行为，`config-version` 已是 2 的盘重跑是 no-op。

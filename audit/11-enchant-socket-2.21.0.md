# v2.21.0 · 附魔镶嵌的一窝 bug

服主原话：

> 然后附魔镶嵌你又留了一堆bug，多附魔的一本附魔书敲上去能突破附魔槽位上限。

审下来确实是**一只窝**：一个方法里挤了四个 bug，不是四个独立失误，
而是同一个根本原因——**判定逻辑埋在 `socketEnchant(Player)` 里，要造玩家才能测，
所以从来没被自检覆盖过**。

自检 393 → **399**。

---

## 一、你报的那个：越限

```java
int consumed = enchants.size();
boolean allMerged = true;          // ← 「书上的附魔是不是全都已在装备上」
for (var ench : usable) { ... }
if (!allMerged && consumed >= sockets) { 拒绝; }
```

`allMerged` 是**整本书**的属性，不是「这本书会新增几条」。于是：

| 场景 | allMerged | consumed | sockets | 判定 | 结果 |
| --- | --- | --- | --- | --- | --- |
| 1 孔，空装备，书带 3 条 | false | 0 | 1 | `0 >= 1` 为假 → **放行** | 写成 **3/1** |

只要有**一条**附魔不在装备上，整个检查就短路了。

### 修法：数「会新增几条」

```java
int remaining = sockets - enchants.size();
if (toAdd.size() > remaining) { 整本拒绝 }
```

拒绝而不是「镶进去一部分」：书是一次性消耗的，镶一半等于把另一半吞掉。
拒绝时明说「这本书要占 N 个孔，你还剩 M 个」，让玩家去开孔或分书敲。

---

## 二、顺手抓出来的另外三个

### 2.1 附魔降级

```java
int level = Math.max(1, Math.min(ench.getMaxLevel(), stored.getOrDefault(ench, 1)));
meta.addEnchant(ench, level, true);   // ← 无条件写，force=true
```

锋利 V 的剑上敲一本锋利 III 的书，**等级被打回 III**。带上 force 的 `addEnchant`
是覆盖语义，而旧代码只在一个分支里检查了「有没有升级」。

修法：分类成「新增 / 升级 / 没变化」，只有 `want > existing.level()` 才写。

### 2.2 互斥附魔能共存

原版不允许锋利与亡灵杀手共存，但**别的插件或改包能造出这种书**。
`canEnchantItem` 只判「这件装备能不能附这个魔」，不判互斥，于是两条都能落地，
得到一把原版规则下不可能存在的剑——留着就是后续所有附魔计算的脏数据源。

修法：书内两两互斥 → 拒；书与装备已有附魔互斥 → 拒。

### 2.3 提示里的分母是错的

```java
"（" + (gems.size() + enchants.size()) + "/" + sockets + "）"
```

`sockets` 是**附魔**孔数，前面却把宝石数量加进去了。镶了 3 颗宝石的装备，
敲第一本书就显示「4/2」。纯粹误导，已改成只算附魔池。

## 三、第四个：账目和原版脱钩（这一条比上面都严重）

`enchantsOf(item)` 只读 `Keys.ENCHANTS` 这个字符串表。但物品上**真实存在**的附魔
还有另一个来源——原版 `meta.getEnchants()`：

- v2.10 之前的老物品（那时候还没有这个表）
- 别的插件 / 管理员 `/give` 直接带附魔
- 任何还没被管的写入路径

表里少算 → 已用孔数偏小 → **可以继续镶到超限**，而且 Lore 上那个「附魔 a/b」
的数字是错的。

修法：改成**并集**——PDC 表 ∪ 原版附魔表，同名取更大等级（绝不用原版值把等级改小）。

这条是「上限只看这一张表」带来的结构性风险：只要有一条写入路径绕过表，
限制就形同虚设。并集之后「已用孔数」永远不小于真实附魔数，只会更严。

---

## 四、为什么这一窝 bug 能活这么久

`planEnchant` 之前不存在。判定、计费、写物品、发消息全在一个 130 行的
`socketEnchant(Player)` 里，**要造一个 Player 才能断言**——而自检跑在无人的测试服上，
所以这块从来没有覆盖。

这次把判定抽成纯函数：

```java
public EnchantPlan planEnchant(ItemStack item, Map<Enchantment, Integer> book)

public record EnchantPlan(List<Enchantment> toAdd,
                          Map<Enchantment, Integer> toUpgrade,
                          String reject)
```

`ItemStack + Map` 进、计划出。不扣钱、不写物品、不需要玩家。

**这才是修复的真正内容**：bug 是症状，不可测才是病。下面五条断言现在锁着它：

| # | 断言 |
| --- | --- |
| 1 | 1 孔 + 3 条书 → 被拒，且理由里带上「3」和「1」 |
| 2 | 3 孔 + 3 条书 → 放行，toAdd=3、toUpgrade 空 |
| 3 | 锋利 V + 锋利 III 书 → 拒（不会变）；锋利 III + 锋利 V 书 → 升级且不占新孔 |
| 4 | 书内锋利+亡灵杀手 → 拒（互斥） |
| 5 | 原版附魔没写进 PDC 也算已用孔数；2 孔已用 1 → 再敲 2 条要拒 |

第 1 条就是你报的那个场景，之前**没有任何断言覆盖它**。

---

## 五、附带补上的漏项

`givefull` 发了满配宝石孔，却没给附魔孔——玩家拿到「满配」发现一本书都敲不进去。
补了 `GemService.fillMaxEnchantSockets(item)`（开放到材料档位上限，跳过费用与掷骰），
`givefull` 的回报里也加了「附魔孔 N」。

---

## 六、仍然没做的（说明白，不藏）

- **附魔拆卸**：镶上去就只能靠原版砂轮（已被拦），没有「取回附魔」的入口
- **互斥判定只覆盖书 vs 装备**，不覆盖「玩家故意想要两把不同的剑各镶一条」
- **附魔等级上限按 `getMaxLevel()` 夹**：所以超等级（锋利 VI 这种改包书）会被夹回 V。
  这是故意的——原版规则优先于改包数值，但确实意味着「管理员想发超规格附魔」做不到。

（原先这里还记着一条「护甲满配会镶赤玉」的缺陷，已在同轮修掉：
`fillMax` 现在按装备类型给优先级顺序，护甲先给玄铁石 / 金刚石 / 血珀，
武器先给赤玉 / 星辉石 / 破军石，并加了断言锁住。）

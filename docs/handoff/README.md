# 交接报告（handoff）怎么用

这个目录是**跨会话的交接面**。上下文会被压缩，对话里说过的细节会丢；写在这里的东西不会。

## 每轮必读

开工第一件事，按这个顺序读：

1. `docs/handoff/LATEST.md` —— 上一轮的交付报告。**这一份最重要**：
   里面有当前版本号、自检项数下限、压测数字、下一轮该做的清单、以及「不能重犯的坑」。
2. `README.md` 最新一节（`## 十四·补XX`）—— 同一轮的叙事版，有更长的「为什么」。
3. `git log --oneline -3` —— 确认上一轮真的提交并推送了。

**不要靠回忆**：报告里写了「下一轮先做这 4 条」，就不要自己想新花样。

## 每轮必写

一轮做完（构建绿 + 自检 0 失败 + 压测 FAIL 0 + README 已更新）之后，写报告：

1. 新建 `docs/handoff/archive/v<版本号>.md`，内容按 `v2.25.6.md` 的结构抄：
   一分钟状态 / 本轮改了什么（带 文件:行号）/ 下一轮先做这几条 / 不能重犯的坑 /
   命令速查 / 60 秒自查 / 交付物清单。
2. 把它复制成 `docs/handoff/LATEST.md`（覆盖）。
3. 和代码同一个 commit 提交。

归档文件**永不修改**，只新增。这样任何一轮都能回溯「当时到底改了什么、为什么」。

## 写报告的三条要求

- **写给「失忆的自己」看**：不要写「如上所述」「前面提到过」，每一条自带上下文。
- **带位置**：`文件:行号`。下一轮照着就能下手，不用重新搜。
- **带判据，不只带结论**：不是「这处有 bug」，而是「这处扣 A 账、退 B 账，`coin-sinks=server` 时能 1:1 洗钱」。

## 为什么不放在 `.workbuddy/`

`.workbuddy/` 被 gitignore（本地规则/记忆，机器一换就没了）。
交接报告必须**进版本库**：换机器、重装、换人接手都还在。
